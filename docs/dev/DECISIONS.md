# DECISIONS — journal des décisions d'architecture (ADR)

Format : une entrée par décision, 5 à 10 lignes. Ajoute une entrée dès que tu tranches une ambiguïté du cahier des charges ou que tu t'écartes d'une recommandation.

## ADR-001 — Vérification des reçus store : directe, sans RevenueCat (2026-11-04)

Contexte : §8.1 laisse le choix entre vérification directe et RevenueCat (sous-traitant hors UE).
Décision : vérification directe derrière une interface `StoreReceiptVerifier` ; RevenueCat reste possible plus tard via un adaptateur.
Conséquence : moins de dépendance RGPD, un peu plus de code (App Store Server API + Google Play Developer API).

## ADR-002 — Dates calendaires en `string` + `Temporal.PlainDate` via polyfill `temporal-polyfill` (2026-11-04)

Contexte : NF-FMT-08 autorise chaîne ou Temporal.
Décision : type `CalendarDate = string & { __brand }` aux frontières (API, base, JSON), `Temporal.PlainDate` pour tout calcul dans `packages/shared`.
Conséquence : aucune occurrence de `new Date(` sur une date calendaire ; règle ESLint `no-restricted-syntax` ajoutée.

## ADR-003 — F-NOT-05 sans mode discret : aucune notification ne contient de montant (2026-11-04)

Contexte : F-NOT-05 (M) dépend du « mode discret » F-AUTH-05, qui est S (hors MVP). §8.1 indique « contenu sans montant ».
Décision : au MVP, aucune notification push ne contient de montant, quel que soit le réglage. Le mode discret (F-AUTH-05) reste au backlog.
Conséquence : F-NOT-05 satisfaite trivialement et testée (aucun montant dans les charges utiles). Si F-AUTH-05 arrive en V1, les montants pourront être ajoutés hors mode discret.

## ADR-004 — « Dépassement significatif » = chaque tranche de 10 % au-delà de 100 % (2026-11-04)

Contexte : F-LIM-04 ne définit pas « dépassement significatif ».
Décision : alertes à 80 %, 100 %, puis 110 %, 120 %, … de la limite en vigueur ; une seule alerte par seuil et par période (clé d'unicité `limit:<notebook>:<période>:<seuil>`).
Conséquence : nombre d'alertes borné, idempotence simple ; le pas (10 %) est une constante modifiable.

## ADR-005 — « Dépense inhabituellement élevée » (2026-11-04)

Contexte : F-NOT-01 cite une alerte de dépense inhabituellement élevée sans la définir.
Décision : une dépense est inhabituelle si son montant ≥ 3 × la médiane des dépenses de la même catégorie racine sur les 90 jours précédents, avec au moins 5 dépenses d'historique et un montant ≥ 20 € (2000 centimes).
Conséquence : calcul simple côté API, pas de faux positifs sur un historique vide ; la notification ne contient pas le montant (ADR-003).

## ADR-006 — Node 22 cible, Node local plus récent toléré (2026-11-04)

Contexte : la cible est Node 22 (o2switch, §8.1), le poste de développement a Node 26 et aucun gestionnaire de versions.
Décision : `.nvmrc` = 22, `engines.node` = `>=22`, `@types/node` 22.x épinglé (le typecheck refuse les API absentes de Node 22), CI exécutée en Node 22.
Conséquence : la CI fait foi ; les écarts de comportement d'exécution 22/26 sont détectés en CI.
Contrainte liée : TypeScript épinglé à 6.0.x, car typescript-eslint 8.72 exige `typescript <6.1.0` (TypeScript 7 natif non supporté). Monter TypeScript seulement après avoir vérifié ce peer.

## ADR-007 — Une migration par fonctionnalité plutôt qu'un schéma complet en P1-03 (2026-11-04)

Contexte : le plan initial créait toutes les tables en P1-03 ; §8.2 demande « une migration par changement ».
Décision : P1-03 crée l'outillage et les tables de comptes, d'audit et de file de tâches ; chaque tâche qui introduit une table ajoute sa migration. Le test « invariants de schéma » parcourt toutes les tables présentes, donc couvre automatiquement les suivantes.
Conséquence : tâches plus petites, schéma conçu avec les tests de la fonctionnalité.

## ADR-010 — Base locale et CI : docker-compose unique, trois comptes, réglages serveur en filet (2026-11-04)

Contexte : §8.2 et NF-QUA-03 imposent MariaDB 10.6, utf8mb4_unicode_520_ci et trois comptes distincts (API, migrations, back-office) sans fixer noms ni variables.
Décision : `docker-compose.yml` (image `mariadb:10.6`, port 3307) crée les bases `depenseo` (renommée `depenseo_dev` par ADR-066) et `depenseo_test` et les comptes `depenseo_api` / `depenseo_admin` (DML seul) et `depenseo_migrator` (tous droits sur ces bases). Le serveur imite un mutualisé : utf8mb4 et `STRICT_ALL_TABLES`, mais fuseau `SYSTEM` = Europe/Paris et `REPEATABLE-READ` laissés exprès, pour que les tests de P1-02 prouvent que l'API force `+00:00` et READ COMMITTED à chaque connexion. Image épinglée au patch (`mariadb:10.6.28`), port lié à 127.0.0.1. La CI (P0-03) démarre ce même compose puis `scripts/db-wait.sh`, plutôt qu'un service GitHub séparé, pour n'avoir qu'une définition. `scripts/db.test.mjs` fait partie de `pnpm test` : la base doit être démarrée.
Conséquence : mots de passe de développement par défaut (sans apostrophe), surchargeables via `.env` (`.env.example`) ; les tests d'intégration nettoient la base avec le compte de migration.

## ADR-011 — Montants, devises et saisie dans `packages/shared` (2026-11-04)

Contexte : NF-FMT-01/06/08 et F-DEP-02 ne fixent ni signe, ni bornes, ni décimales par devise, ni règles de saisie au-delà de « virgule ou point ».
Décision : `Cents` = entier sûr signé (le signe est une règle métier, pas de type). Les « centimes » sont les unités mineures de la devise ; leur nombre de décimales vient d'une **table ISO 4217 figée** dans `currency.ts` (EUR 2, JPY 0, TND 3, HUF 2), pas d'Intl/ICU dont les données varient selon le moteur (HUF, MGA à 0 dans ICU) et changeraient la valeur stockée. `CurrencyCode` = code présent dans cette table (devises européennes et de la zone francophone ; à étendre par ajout). `formatAmount` passe à `Intl.NumberFormat` une chaîne décimale exacte avec les décimales ISO forcées, sans division flottante. `parseAmountInput` (MVP en euros, 2 décimales) : sans signe, un seul séparateur décimal (`,` ou `.`), au plus 2 décimales, espaces (normale, insécable, fine U+2009, fine insécable) seulement entre groupes de 3 chiffres, saisie > 40 caractères refusée (`too_large`) ; « 1.234,56 » et « 1,234.56 » sont refusés plutôt que devinés ; résultat `{ ok, cents } | { ok: false, error }` sans exception. `CalendarDate` validée sans `Date` (calendrier grégorien, bissextiles, années 1000–9999 comme SQL `DATE`).
Conséquence : « 1.234 » (trois décimales) est refusé et non lu comme 1 234 € ; l'interface devra afficher l'erreur `too_many_decimals`.

## ADR-012 — Périodes de limite : repli fin de mois, semaine ISO, « aujourd'hui » par instant explicite (2026-11-04)

Contexte : F-LIM-02 permet un début de période au jour du mois (ex. le 28) ou au jour de la semaine (lundi par défaut), sans dire ce qui arrive aux jours 29–31 dans les mois plus courts.
Décision : la période mensuelle de début `N` commence chaque mois le jour `min(N, nombre de jours du mois)` et finit la veille du début suivant. Avec `N = 31` : 31 janv.–27 févr., 28 févr.–30 mars, 31 mars–29 avr., 30 avr.–30 mai. Les périodes se touchent toujours, sans trou ni chevauchement. Le jour de début de semaine suit la numérotation ISO (1 = lundi … 7 = dimanche), lundi par défaut. `todayIn(timeZone, instant)` prend un `Temporal.Instant` explicite (horloge injectée, jamais l'heure système) et ne dépend pas du fuseau du processus. Le polyfill `temporal-polyfill` (1.0.7, épinglé) est importé explicitement, même si Node 26 fournit `Temporal`, car la cible reste Node 22.
Conséquence : une période peut durer de 28 à 31 jours. Le fuseau est validé par Temporal (`RangeError` si inconnu).

## ADR-013 — Squelette API : NestJS 12 ESM, pino expurgé, erreurs problem+json, OpenAPI committé (2026-11-04)

Contexte : P1-01 fixe la config par env, le journal expurgé, RFC 7807 et `openapi.json`, sans choisir les bibliothèques, la liste des variables ni la forme exacte des journaux.
Décision : `@depenseo/api` en ESM (NestJS 12.3, `"type": "module"`, NodeNext), versions épinglées. Les tests Vitest s'appuient sur le transformeur de Vite 8 qui émet les métadonnées de décorateurs (`emitDecoratorMetadata` du tsconfig), sans SWC. Configuration validée par zod dans `src/config/env.ts` : `NODE_ENV`, `PORT` (3000), `LOG_LEVEL` (info), `JWT_ACCESS_SECRET` (≥ 32 caractères, obligatoire dès maintenant pour que le refus de démarrer soit réel). Les tâches suivantes ajoutent leurs variables (base en P1-02) dans le même schéma. Le message d'erreur nomme la variable, jamais la valeur. Journal JSON par `nestjs-pino` : la requête est réduite à `id`, `method`, `path` sans chaîne de requête, et la réponse à `statusCode`. Aucun en-tête ni corps n'est journalisé, et `formatters.log` expurge récursivement les clés `amount*`, `*email*`/`mail`, `*password`, `*token*`, `*secret`, `note(s)`, `merchant`, `authorization`, `cookie`, `set-cookie`, `phone*`, `iban`, `display|first|last|full_name` (liste de référence : `SENSITIVE_KEY` dans `redact.ts`). pino `redact` n'est pas utilisé parce qu'il ne sait pas filtrer sur un préfixe de clé. Erreurs : un filtre global renvoie `application/problem+json` (`type: about:blank`, `title` = phrase HTTP, `status`, `instance` = chemin sans requête). `detail` ne figure que pour une `ProblemException` (classe de l'API), jamais pour les autres `HttpException`, car Nest recopie le message de body-parser, qui contient l'entrée reçue. Une erreur inattendue donne un 500 générique et est journalisée réduite à `type`, `code` et pile sans la ligne de message (un message de pilote comme « Duplicate entry 'a@b.fr' » peut porter des données personnelles). `redactDeep` ne descend que dans les objets simples et les tableaux (pino applique `formatters.log` avant les serializers). Pas de CORS, pas d'en-tête `X-Powered-By`, pas d'interface Swagger servie : le contrat est `apps/api/openapi.json`, généré par `pnpm --filter api openapi` (build tsc puis `dist/scripts/openapi.js`), exclu de Prettier et comparé octet à octet par un test. Entrée Passenger : `dist/src/main.js` (voir P7-07). Le postinstall de `@scarf/scarf` (télémétrie apportée par `@nestjs/swagger`) est bloqué par `pnpm.neverBuiltDependencies`.
Conséquence : toute route nouvelle impose de régénérer `openapi.json`, sinon le test échoue. Un message d'erreur en texte libre n'est pas expurgé : ne jamais y interpoler de donnée personnelle.

## ADR-014 — Couche données : pool mysql2 réglé à chaque connexion, retry de transaction, UUID binaires (2026-11-04)

Contexte : §8.2 et NF-FMT-07 imposent le mode chaîne pour `DATE`, `+00:00`, READ COMMITTED et le retry 1213/1205, sans fixer la configuration ni la taille du pool, ni l'ordre des octets des UUID.
Décision : une seule variable `DATABASE_URL` (`mysql://compte:mot_de_passe@hôte:port/base`, compte API) et `DB_POOL_SIZE` (5 par défaut, 1–20) : chaque processus Passenger a son pool et le mutualisé limite les connexions, d'où une petite valeur. Le pool est le pool **à rappels** de mysql2 (le pool à promesses retransmet l'événement `connection` avec la connexion brute) ; à l'ouverture de chaque connexion physique, `SET time_zone = '+00:00'` puis `SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED` (deux requêtes, sans `multipleStatements`, SQL commun MySQL 8 / MariaDB 10.6) ; une erreur détruit la connexion (les requêtes en file sont rejetées) et est journalisée par code seul. Une seule connexion inactive est gardée (`maxIdle: 1`, les autres ferment après 60 s). `DATABASE_URL` sans nom de base ou avec paramètres de requête est refusée. La collation `utf8mb4_unicode_520_ci` est négociée à la poignée de main (`charset`). Pilote : `dateStrings: ['DATE']`, `timezone: 'Z'`. Le pool ne se connecte qu'à la première requête : démarrer l'API ou générer OpenAPI n'exige pas la base. `withTransaction(db, fn)` rejoue **toute** la transaction (5 tentatives, attente 20 ms × 2ⁿ plus gigue) si la chaîne `cause` contient `errno` 1213 ou 1205 : `fn` ne doit avoir aucun effet hors base. UUID v7 (`uuid` 14) stockés en `BINARY(16)` dans l'ordre des octets du texte (pas d'échange de type `UUID_TO_BIN(…, 1)`, inutile pour v7 déjà triés par date) ; colonne Drizzle `uuidBinary` exposée en chaîne.
Conséquence : les tests d'intégration lisent `TEST_DATABASE_URL` (défaut : compte API sur `depenseo_test`) et `TEST_MIGRATOR_URL` pour le DDL de leurs tables jetables, préfixées `zz_test_` et supprimées en fin de test. `drizzle(pool)` s'écrit en forme positionnelle : drizzle-orm 0.45.4 prend un objet `{ client, mode }` pour le client lui-même.

## ADR-015 — Migrations drizzle-kit, schéma du socle et règles d'invariants (2026-11-04)

Contexte : P1-03 exige des migrations SQL versionnées rejouables et un contrôle des invariants sur toutes les tables ; le cahier ne fixe ni les colonnes de statut, ni la famille des jetons, ni la définition d'une « table synchronisée ».
Décision : le schéma Drizzle (`apps/api/src/db/schema/`) est la source ; `pnpm --filter api db:generate` (drizzle-kit 0.31.11, hors ligne) écrit le SQL dans `apps/api/drizzle/` (committé, `meta/` exclu de Prettier). L'application passe uniquement par `runMigrations(url)` (migrateur de drizzle-orm, table `__drizzle_migrations`), via `pnpm --filter api migrate` et `MIGRATOR_DATABASE_URL` (compte DDL, jamais celui de l'API) ; jamais `drizzle-kit migrate/push`. Une migration déjà appliquée ne se modifie pas. La première migration commence par un `ALTER DATABASE … utf8mb4_unicode_520_ci` ajouté à la main : drizzle-kit n'écrit pas de collation de table, les tables héritent donc de celle de la base (souvent latin1 ou general_ci sur cPanel). Horodatages `DATETIME(3)` fournis par l'application (horloge injectable), sans `DEFAULT CURRENT_TIMESTAMP`. Statuts, rôles, objets de jeton en `VARCHAR` + union TS (pas d'`ENUM`, plus simple à faire évoluer). Pas de colonne `JSON` : MariaDB l'implémente en LONGTEXT `utf8mb4_bin`, ce qui violerait la collation commune ; charges utiles en `TEXT` validées par zod. Jetons (refresh, e-mail) stockés par empreinte SHA-256 `BINARY(32)` (type `sha256Binary` : le `binary()` de Drizzle décode les octets en UTF-8) ; `refresh_token.family_id` porte la famille de rotation. `audit_log` sans clé étrangère (la trace survit à la suppression d'un compte) et sans donnée personnelle. Une table est **synchronisée** si elle a une colonne `notebook_id` : elle doit alors avoir `updated_at`, `deleted_at` et l'index `(notebook_id, updated_at, id)`. Montants à venir : `bigint(…, { mode: 'number' })` (le pilote rend une chaîne au-delà des entiers sûrs, à rejeter par l'application).
Conséquence : `test/support/schema-invariants.ts` contrôle toutes les tables de la base sauf `__drizzle_migrations` et `zz_test_*` : collation de table et de colonne, InnoDB, ni FLOAT/DOUBLE/REAL/TIMESTAMP, `DATETIME(3)`, `id` clé primaire et toute colonne `*_id` en `binary(16)`, règle de synchronisation. Le `globalSetup` de vitest vide `depenseo_test` (garde-fou sur le suffixe `_test`) puis la migre depuis zéro à chaque lancement.
Compléments (relecture P1-03) : `runMigrations` prend `GET_LOCK('depenseo_migrate', 60)` (deux lancements ne s'entrelacent pas). Le DDL valide implicitement la transaction du migrateur : une migration interrompue laisse des objets créés sans ligne dans `__drizzle_migrations`. Reprise manuelle : supprimer les objets créés par la migration fautive (ou finir le DDL à la main et insérer la ligne `hash, created_at` du journal), puis relancer ; garder les migrations courtes, une préoccupation par fichier. `__drizzle_migrations` est créée avant l'`ALTER DATABASE` et peut garder une autre collation (exclue du contrôle). La règle `*_id` → `binary(16)` vise nos identifiants : un identifiant externe (achat, `sub` Apple/Google) prendra un autre suffixe (`*_ref`, `*_sub`). Le test d'invariants contrôle aussi, par nom : `amount`/`*_amount` en `bigint`, `currency`/`*_currency` en `char(3)`, `rate`/`*_rate` en `decimal(18,8)`. `notebook` n'a pas de `notebook_id` : sa synchronisation (renommage, suppression) passera par `updated_at`/`deleted_at` filtrés par l'appartenance, à traiter avec la synchronisation. `notebook_member_uq` : réinviter un membre retiré réactive la ligne. E-mail unique insensible à la casse et aux accents (collation) : normaliser en minuscules à l'écriture. Index `expires_at` pour les purges et conservation de `audit_log` : à ajouter avec les tâches de purge.

## ADR-016 — File de tâches : réclamation par bail, délais 1-2-4-8 min, purge des seules tâches réussies (2026-11-04)

Contexte : §8.2 impose une table `job` alimentée dans la transaction de la donnée, un cron d'au plus 50 s par minute avec `SELECT … FOR UPDATE SKIP LOCKED`, `GET_LOCK` pour la planification, un délai croissant, l'échec après 5 essais et une purge à 7 jours, sans fixer les délais, la reprise d'un worker interrompu ni la forme des charges utiles.
Décision :
- **Ajout** : `JobQueue.enqueue(tx, définition, payload, { runAt?, uniqueKey? })` (`src/jobs/job-queue.ts`) prend le `tx` de l'appelant. Un doublon de `unique_key` ne fait rien (`ON DUPLICATE KEY UPDATE id = id`) et renvoie la tâche existante (`created: false`), relue par sa clé : mysql2 active `CLIENT_FOUND_ROWS`, `affectedRows` ne distingue pas les deux cas. La clé reste prise tant que la ligne existe, y compris par une tâche `failed`.
- **Charge utile** : `defineJob(type, schéma zod)` la valide, puis `assertNoPersonalData` refuse toute clé sensible (`SENSITIVE_KEY` de `redact.ts` : montant, e-mail, note, jeton…) et toute chaîne contenant `x@y` ; 4 Kio sérialisés au plus. Elle ne porte que des identifiants : le gestionnaire relit le reste en base.
- **Réclamation** (`job-runner.ts`) : seulement les types qui ont un gestionnaire, une tâche à la fois, dans une courte transaction. D'abord un bail expiré (`status = running AND locked_until < now`, index `(status, locked_until)`), sinon la plus ancienne tâche due (`status = pending AND run_at <= now ORDER BY run_at, id`, index `(status, run_at)`), toujours `FOR UPDATE SKIP LOCKED`. Deux requêtes plutôt qu'un `OR` : avec `OR`, le plan trie hors index et InnoDB verrouille toutes les lignes dues, si bien qu'un second worker ne trouve rien (constaté sur MariaDB 10.6). La réclamation incrémente `attempts` et pose un bail `locked_until` de 5 min. Un bail expiré au 5ᵉ essai passe directement `failed` (`lease_expired`), sans nouvelle exécution.
- **Exécution** : le gestionnaire s'exécute hors transaction, avec un délai de `min(30 s, temps restant du passage)` et un `AbortSignal`. Aucune réclamation s'il reste moins de 10 s (même si la planification a consommé le budget) : le passage tient dans 50 s. La clôture (dans `withTransaction`) est gardée par `(status = running, attempts = n)` : un worker en retard n'écrase pas une reprise, il compte `stale` et journalise `job settle skipped`.
- **Échec** : la tâche repasse `pending` à `maintenant + 1, 2, 4 puis 8 min`, puis passe `failed` au 5ᵉ essai, ou tout de suite si la charge utile est illisible (`invalid_payload`). `last_error` et les journaux ne gardent qu'un code court (`error.code` s'il est simple, sinon le nom de classe), jamais le message ni la charge utile.
- **Passage cron** (`scripts/jobs-run.ts`, `pnpm --filter api jobs:run`) : d'abord les tâches périodiques sous `GET_LOCK(nom, 0)`, exécutées sur la connexion dédiée qui tient le verrou (un pool d'une connexion attendrait sinon indéfiniment ; si `RELEASE_LOCK` échoue, la connexion est détruite au lieu d'être rendue), avec `nom = depenseo.jobs.<sha256(base)[0..32]>` (les verrous valent pour tout le serveur mutualisé, longueur fixe ≤ 64 pour MySQL 8). Ensuite la file, jusqu'à 50 s après le démarrage. La purge supprime par lots de 1 000 les tâches `done` terminées depuis plus de 7 jours (index `(status, finished_at)`). Les `failed` restent pour diagnostic. Le script ne lit que `DATABASE_URL`, `DB_POOL_SIZE`, `LOG_LEVEL` et `NODE_ENV` (`loadWorkerConfig`). Le temps vient d'une horloge injectable (`src/clock.ts`), jamais de `NOW()` SQL.
Conséquence : les gestionnaires doivent être idempotents (rejeu après un bail expiré) et respecter `signal`. Après un dépassement de délai, la tâche est replanifiée (+1 min) et son bail effacé : un gestionnaire qui ignore `signal` n'est arrêté que par la fin du processus cron (`process.exit`), et pourrait sinon s'exécuter en double. Le délai des gestionnaires utilise de vrais minuteurs, pas l'horloge injectée. Une tâche dont le type n'a aucun gestionnaire reste `pending` indéfiniment. Nouveaux gestionnaires et tâches périodiques : `src/jobs/registry.ts`. La crontab o2switch (`* * * * *`) est à configurer au déploiement (P7). La purge des `failed` sera décidée avec la console d'administration. Migration `0001_job_claim_indexes`.

## ADR-017 — Inscription : argon2id, lien de vérification 24 h tiré à l'envoi, réponse 202 sans énumération (2026-11-04)

Contexte : F-AUTH-01 (« inscription par e-mail et mot de passe, avec vérification de l'e-mail ») ne fixe ni règles de mot de passe, ni durée du lien, ni comportement pour une adresse déjà inscrite, ni la connexion avant vérification (exigée par PLAN P1-05).
Décision :
- **Mot de passe** : 8 à 128 caractères, aucune règle de composition (NIST SP 800-63B). Empreinte argon2id (`@node-rs/argon2`, binaire précompilé sans script d'installation) aux paramètres minimaux OWASP : 19 Mio, 2 passes, 1 fil. Toujours calculée à l'inscription, et une vérification factice est faite pour un compte inconnu, pour un temps de réponse homogène.
- **`POST /api/v1/auth/register`** `{ email, password, acceptTerms: true, language?: fr|en }` → **202 sans corps** dans tous les cas valides. L'adresse est stockée sans espaces et en minuscules (ADR-015). `acceptTerms` est obligatoire et date à la fois `terms_accepted_at` et `privacy_accepted_at` (une seule case CGU + confidentialité, §6). Adresse déjà inscrite et **vérifiée** : rien n'est modifié ni envoyé. Adresse inscrite **non vérifiée** : le mot de passe, la langue et les consentements sont **remplacés**. Les liens déjà envoyés restent valides : un lien n'est pas lié au mot de passe et n'arrive que chez le titulaire de l'adresse ; les invalider ne protégerait rien et laisserait l'utilisateur sans lien une fois le plafond atteint. Sans cela, un tiers pourrait pré-inscrire l'adresse d'autrui avec son propre mot de passe : la victime, en cliquant le lien, vérifierait un compte dont le tiers connaît le mot de passe (relecture P1-05). Risque résiduel : un tiers qui se réinscrit entre l'inscription de la victime et son clic impose son mot de passe ; la connexion de la victime échoue alors et la réinitialisation (P1-07, qui révoque les sessions) reprend la main. Un nouveau lien est programmé sauf si un envoi est déjà en attente (il tirera son jeton après le remplacement) ou si 3 envois ont déjà été programmés dans l'heure glissante (`unique_key = verify-email:<userId>:<uuid>`, préfixe indexé). Deux inscriptions simultanées sont sérialisées par le verrou de l'upsert.
- **E-mail** : tâche `mail.verify_email` `{ userId }` mise en file dans la transaction de création. Le jeton (32 octets aléatoires, base64url) est **tiré par le gestionnaire au moment de l'envoi**, car seule son empreinte SHA-256 est stockée (`email_token`) et la charge utile ne peut pas porter de secret (ADR-016). Un rejeu produit un second lien valide, sans conséquence. Validité 24 h. Lien `PUBLIC_WEB_URL/verify-email#token=…` : jeton dans le fragment, jamais transmis au serveur web ni journalisé ; la page (web) et le lien universel (mobile) sont à faire dans leurs lots. Texte brut fr/en selon `user.language`.
- **`POST /api/v1/auth/verify-email`** `{ token }` → 204 ; jeton inconnu, expiré ou déjà consommé → 400 (même message). Consommation par `UPDATE … WHERE consumed_at IS NULL AND expires_at > now` puis contrôle de `affectedRows` : mysql2 active `CLIENT_FOUND_ROWS` (lignes trouvées), qui valent ici les lignes modifiées puisque `consumed_at` passe de NULL à une date : usage unique même en concurrence (testé à 8 appels simultanés).
- **Connexion avant vérification** : `AuthService.authenticate` (route et jetons en P1-06) renvoie 401 « Identifiants invalides » pour adresse inconnue ou mauvais mot de passe, et 403 « Adresse e-mail non vérifiée » seulement après un mot de passe correct.
- **Mailer** : interface `Mailer` (`src/mail/mailer.ts`), `InMemoryMailer` (tests), `SmtpMailer` (nodemailer, délais connexion/accueil/socket de 15 s) qui relance les erreurs sans message (code `smtp_<code réponse SMTP ou code nodemailer>`). Un refus définitif (5xx) est retenté comme les autres erreurs (5 essais) : distinguer les erreurs définitives demandera une évolution du moteur de tâches. Variables du cron seulement (`loadMailConfig`) : `SMTP_URL` (smtp/smtps), `MAIL_FROM`, `PUBLIC_WEB_URL` (https, origine seule). Elles sont obligatoires : sans elles, tout le passage cron échoue (purge comprise), pour qu'une configuration incomplète se voie au déploiement plutôt que par des e-mails jamais envoyés. Horloge Nest injectable (`ClockModule`, jeton `CLOCK`, `createApp({ clock })`).
Conséquence : pas de limitation de débit avant P7-03 : chaque inscription coûte un calcul argon2 (19 Mio), et les envois sont bornés à 3 par heure et par adresse. P1-08 (Apple/Google) ne devra rattacher qu'un compte à l'adresse vérifiée, et effacer le mot de passe d'un compte non vérifié qu'il rattache. Corps validés par zod via `parseBody` (`src/http/parse-body.ts`), `detail` = noms de champs seuls. Le carnet personnel créé à l'inscription viendra en P1-09.

## ADR-018 — Sessions : JWT HS256 de 15 min, refresh opaque 30 j à rotation, famille révoquée sur réutilisation, garde globale (2026-11-04)

Contexte : NF-SEC-02 fixe seulement « jetons d'accès courts (15 min) et jetons de rafraîchissement révocables » ; ni durée du refresh, ni routes, ni portée de la déconnexion.

- **Routes** (publiques) : `POST /api/v1/auth/login` `{ email, password }` → 200 `{ tokenType: "Bearer", accessToken, expiresIn: 900, refreshToken, refreshExpiresIn }` (401 identifiants invalides, même corps pour adresse inconnue ; 403 adresse non vérifiée, ADR-017). `POST /auth/refresh` `{ refreshToken }` → 200 même forme. `POST /auth/logout` `{ refreshToken }` → 204 toujours (jeton inconnu compris). Réponses à jetons : `Cache-Control: no-store`. Corps mal formé → 400.
- **Jeton d'accès** : JWT HS256 (`jose` 6.2.15, aussi utilisé par P1-08), clé `JWT_ACCESS_SECRET` (≥ 32 caractères), `iss=depenseo`, `aud=depenseo-api`, `sub`=UUID du compte, `iat`, `exp=iat+900`. Vérifié avec l'horloge applicative (`currentDate`) : expiré dès `exp <= now` (15 min pile). Algorithme imposé (`alg: none` et autres refusés). Sans état : un jeton reste valide ≤ 15 min après déconnexion ou révocation (risque accepté, cohérent avec « jetons courts »).
- **Jeton de rafraîchissement** : opaque, 32 octets base64url (`opaque-token.ts`, partagé avec les liens e-mail), seule l'empreinte SHA-256 est stockée. Validité **30 jours glissants** : chaque rotation émet un jeton neuf pour 30 j. Pas de durée absolue de session (à revoir avec F-AUTH-06 « appareils connectés », V1).
- **Famille** = la session d'un appareil, née à la connexion (`family_id`). Refresh et déconnexion lisent la ligne du jeton, verrouillent la ligne `user` du titulaire (`SELECT … FOR UPDATE`) puis relisent le jeton : les opérations de session d'un compte sont sérialisées. Sans ce verrou, sous READ COMMITTED (pas de verrou de plage), une révocation de famille concurrente d'une rotation pouvait manquer le successeur non encore validé (relecture P1-06). P1-07 (reset) devra prendre le même verrou. **Rotation** : jeton libre et non expiré → `used_at = now` et insertion du successeur dans la même famille, même transaction. **Réutilisation** (jeton déjà utilisé ou révoqué) → 401 et révocation de toute la famille (transaction validée avant le 401). Jeton simplement expiré (`expires_at <= now`) → 401 sans révocation.
- **Purge** : tâche périodique `purge-expired-refresh-tokens` (registre P1-04, par lots de 1 000, index `refresh_token_expires_idx`, migration 0002) supprime les jetons expirés. Un jeton expiré purgé donne le même 401 ; seule la révocation de famille sur sa réutilisation est perdue, sans objet (ses successeurs ont leur propre échéance).
- **Pas de délai de grâce** : deux échanges simultanés du même jeton (ex. deux requêtes parallèles de l'app) → l'un réussit, l'autre est traité en réutilisation et révoque la famille (l'appareil doit se reconnecter). Le client mobile doit sérialiser ses rafraîchissements (à respecter en P5).
- **Déconnexion** : révoque la famille du jeton présenté (cet appareil seulement), même si ce jeton a déjà été échangé. « Déconnecter partout » = F-AUTH-06 (V1) ; la réinitialisation du mot de passe (P1-07) révoquera toutes les familles du compte.
- **Garde globale** `AccessTokenGuard` (`APP_GUARD`) : toute route exige `Authorization: Bearer <jwt>` (schéma insensible à la casse) sauf `@Public()`, posé **route par route** ; la liste blanche (sonde, `auth/register|verify-email|login|refresh|logout`, puis `password-reset/request|confirm` en P1-07) est figée par `test/auth/public-routes.spec.ts`, qui appelle sans jeton chaque route de l'OpenAPI. 401 avec `WWW-Authenticate: Bearer` (RFC 6750). `@CurrentUser()` donne `{ userId }`. `GET /api/v1/me` minimal (`id`, `email`, `no-store`) sert de route protégée de référence ; complété en P1-10. Compte supprimé pendant la validité d'un jeton → 401 sur `/me` ; les gardes de ressources (P1-09) contrôleront l'appartenance.
- **Administration** (invariant 7) : la garde globale passe avant toute garde de route ; sous `/api/v1/admin`, c'est elle qui devra répondre **404** (et non 401) sans rôle admin, à faire avec les routes admin.
- `APP_CONFIG` est fourni par un `ConfigModule` global.

Conséquence : pas d'anti-bruteforce sur `/auth/login` avant P7-03 (limitation de débit), chaque essai coûte un argon2.

## ADR-019 — Réinitialisation du mot de passe : lien e-mail 30 min, toutes sessions révoquées, adresse réputée vérifiée (2026-11-04)

Contexte : F-AUTH-03 fixe « lien à usage unique (validité 30 min) » ; le plan exige une réponse identique que l'adresse existe ou non et la révocation des refresh.

- **Routes** (publiques) : `POST /api/v1/auth/password-reset/request` `{ email }` → **202** toujours (adresse inconnue comprise, corps vide). `POST /auth/password-reset/confirm` `{ token, password }` → 204 ; jeton inconnu, expiré, déjà consommé ou d'un autre usage → 400 « Lien de réinitialisation invalide ou expiré ». Mot de passe : mêmes règles que l'inscription (8–128, ADR-017).
- **Envoi** : tâche `mail.reset_password` (charge `{ userId }`), le jeton opaque est tiré à l'envoi (`email_token`, purpose `reset_password`, empreinte SHA-256), lien `PUBLIC_WEB_URL/reset-password#token=…` (fragment). Plafond **3 envois par heure glissante** et par compte, pas de second envoi tant qu'un est en attente : helper commun `scheduleThrottledMail` (aussi utilisé par la vérification d'adresse). Tout compte existant peut demander un lien, y compris sans mot de passe (futurs comptes Apple/Google, P1-08) : il en obtient un.
- **Expiration** : `expires_at = envoi + 30 min`, refusé dès `expires_at <= now` (30 min pile refusé ; testé à 30 min − 1 s / + 1 s).
- **Confirmation** (une transaction) : lecture du jeton → verrou `user … FOR UPDATE` (comme ADR-018) → consommation conditionnelle (`consumed_at IS NULL AND expires_at > now`, `affectedRows`) → consommation des **autres** liens de réinitialisation non utilisés du compte → nouveau mot de passe (argon2id, calculé avant la transaction) → `revoked_at` sur **tous** les refresh non révoqués du compte. Le verrou sérialise avec les rotations : aucun refresh émis en parallèle ne survit (test à barrière : rotation en cours sur une autre connexion, confirmation en attente, successeur révoqué). Constat de contre-épreuve : la propriété tient même sans ce `FOR UPDATE` (l'`UPDATE user` et le verrou implicite de l'insertion non validée sérialisent déjà) ; il est gardé comme défense en profondeur, sans mutation qui le détecte. La **demande** de lien verrouille aussi la ligne `user` (`FOR UPDATE`) : sinon deux demandes simultanées contournent le plafond (testé). Les JWT d'accès déjà émis restent valides ≤ 15 min (sans état, ADR-018).
- **Adresse vérifiée** : un compte non vérifié qui confirme un lien reçu par e-mail a prouvé la possession de l'adresse → `email_verified_at = now`. Option la plus simple ; évite un compte bloqué au 403 après reset.
- Pas de session ouverte à la confirmation : le client se reconnecte par `/auth/login`. Pas d'e-mail « mot de passe modifié » (non exigé ; à reconsidérer avec P7-03). Pas d'entrée `audit_log` (réservé aux accès administrateurs, NF-SEC-06).

Conséquence : la demande sur adresse inconnue fait moins de travail (pas d'écriture) : écart de temps de réponse mineur, accepté jusqu'à la limitation de débit (P7-03).

## ADR-020 — Connexion Apple / Google : `id_token` vérifié côté API, identité par (fournisseur, `sub`), rattachement par adresse vérifiée (2026-11-04)

Contexte : F-AUTH-02 (« Connexion avec Apple et Google », M) ne précise ni le flux, ni le nonce, ni le rattachement à un compte e-mail existant, ni le consentement CGU pour un compte créé ainsi.

- **Route** (publique) : `POST /api/v1/auth/social` `{ provider: apple|google, idToken, nonce, acceptTerms?: true, language?: fr|en }` → 200, même corps que `/auth/login` (ADR-018), `Cache-Control: no-store`. L'app obtient l'`id_token` par le SDK natif (Sign in with Apple, Google Sign-In) : pas de code d'autorisation ni de secret client côté serveur.
- **Vérification** (`IdTokenVerifier`, implémentation jose `JoseIdTokenVerifier`) : RS256 seul ; clés JWKS du fournisseur (`https://appleid.apple.com/auth/keys`, `https://www.googleapis.com/oauth2/v3/certs`, `createRemoteJWKSet`, cache jose par processus, délai 5 s) ; `iss` = `https://appleid.apple.com` ou `https://accounts.google.com` / `accounts.google.com` ; `aud` ∈ `APPLE_CLIENT_IDS` / `GOOGLE_CLIENT_IDS` (listes séparées par des virgules : bundle ID iOS, Services ID, clients OAuth Android/iOS/web) ; `exp` et âge (`iat`) ≤ **10 min** (`maxTokenAge`, un `id_token` Google vaut 1 h ; `iat` futur refusé), tolérance d'horloge 5 s, horloge applicative ; `sub` (≤ 255), `iat`, `nonce` obligatoires. Liste vide = fournisseur désactivé → **503**. Jeton refusé → **401** « Jeton d'identité invalide ». JWKS injoignable ou illisible (`JWKSTimeout`, `JWKSInvalid`, réponse non 200) → 500 (erreur serveur, pas un refus).
- **Nonce** : l'app tire un nonce aléatoire, transmet son **SHA-256 hexadécimal** au fournisseur et le nonce **brut** à l'API, qui exige `claim nonce == sha256hex(brut)` (même convention pour Apple et Google, celle des SDK Apple). Un `id_token` intercepté ne suffit pas sans le nonce brut. Le serveur ne mémorise pas les nonces (rejeu possible dans les 10 min d'âge maximal ; risque accepté, TLS).
- **Identité** : table `user_identity` (`provider`, `subject_hash` = SHA-256 du `sub`, unique par fournisseur ; migration 0003). Haché parce que le `sub` est sensible à la casse et que la collation `utf8mb4_unicode_520_ci` ne l'est pas. Un compte peut porter plusieurs identités. Une identité déjà rattachée ouvre la session de son compte, quelle que soit l'adresse du jeton (elle peut changer chez le fournisseur ; l'adresse du compte n'est pas mise à jour).
- **Nouvelle identité** : exige une adresse attestée (`email_verified` booléen ou chaîne `"true"`, adresse valide après normalisation ADR-015), sinon **403** « non vérifiée ou inutilisable ». Adresse d'un compte existant → **rattachement**, seulement si le fournisseur **fait autorité** sur l'adresse : Apple toujours ; Google seulement pour `@gmail.com` / `@googlemail.com` ou un compte Workspace (claim `hd` non vide), car Google ne revérifie pas une adresse tierce, qui a pu changer de titulaire (domaine expiré) depuis la création du compte Google (relecture P1-08). Sinon **409** (connexion par e-mail ou réinitialisation) et rien n'est rattaché. Apple est réputé faire autorité même pour une adresse tierce (risque d'adresse réattribuée accepté : `email_verified` toujours vrai chez Apple, pratique courante ; à revoir si abus). Rattachement à un compte vérifié : sans `acceptTerms`, mot de passe conservé. Compte **non vérifié** : traité comme une création (`acceptTerms` exigé, sinon 422) : il devient vérifié, son mot de passe est **effacé**, consentements et langue sont repris du titulaire (tous ont pu être posés par un tiers, ADR-017 ; un mot de passe se redéfinit par réinitialisation, ADR-019). Aucune session ne peut exister sur un compte non vérifié. Adresse inconnue → création d'un compte vérifié sans mot de passe si `acceptTerms: true` (date CGU et confidentialité), sinon **422** : l'app affiche alors le consentement et rejoue la requête. Les adresses relais Apple (`privaterelay.appleid.com`) sont des adresses comme les autres.
- **Concurrence** : le rattachement verrouille la ligne `user` (upsert ou `SELECT … FOR UPDATE`) puis relit l'identité : deux premières connexions simultanées n'en créent qu'une (testé à 6 appels, création et rattachement). Un même `sub` présenté en même temps avec des adresses différentes verrouille des lignes différentes : l'unicité `(provider, subject_hash)` refuse l'un (1062), ou il voit l'identité à la relecture après avoir créé son compte (`IdentityRaced`) ; sa transaction (compte créé compris) est annulée puis **rejouée une fois** et retrouve l'identité (testé, dont un test à barrière : sans l'annulation, un compte orphelin restait). Contre-épreuves : ce rejeu absorbe aussi la course de rattachement, si bien que le retrait du `FOR UPDATE` ne fait échouer aucun test (gardé en défense en profondeur) ; la course « compte créé par une inscription concurrente entre le SELECT et l'upsert » (`created` = id inséré relu) n'est pas testée.
- Pas de révocation du jeton Apple ni d'appel à `appleid.apple.com/auth/revoke` (exigé à la suppression de compte par l'App Store, à traiter avec la suppression de compte). Le carnet personnel est créé aussi sur ce chemin de création (fait en P1-09, ADR-021).
Conséquence : `AuthModule.register(idTokenKeys)` et `createApp({ idTokenKeys })` permettent aux tests d'injecter des JWKS locaux (`test/support/id-tokens.ts`). Contre-épreuve : sans l'option `algorithms`, un jeton RS512 passerait avec un JWK publié sans `alg` (testé).

## ADR-021 — Carnets : carnet personnel à la création du compte, accès par adhésion, garde 404, harnais d'isolement (2026-11-04)

Contexte : §8.3 décrit le carnet (« nom, propriétaire, membres et rôles, personnel par défaut ») sans nom par défaut ni sémantique de refus ; NF-SEC-03 exige qu'un utilisateur ne voie ni ne modifie les données d'un autre. Le partage (F-PAR) est hors MVP.

- **Création** : `createPersonalNotebook(tx, { userId, language, now })` (`src/notebooks/personal-notebook.ts`) insère le carnet (`kind = personal`, `owner_id`) et l'adhésion `owner`, dans la transaction qui crée le compte : `AuthService.register` (si la ligne insérée est la sienne, pas sur réinscription d'un compte non vérifié) et `SocialLoginService.resolve` (branche création ; un rattachement n'en crée pas). Nom par défaut selon la langue du compte : « Mon carnet » / « My notebook ». Pas de route de renommage (non exigé).
- **Accès** = adhésion active (`notebook_member.deleted_at IS NULL`) à un carnet non supprimé, quel que soit le propriétaire : le futur partage n'aura pas à changer la garde. Le rôle (`owner`/`member`) est exposé à la route par `@CurrentNotebook()` ; aucune route MVP ne distingue encore les rôles.
- **Garde** `NotebookAccessGuard`, posée par `@UseGuards` sur toute route dont le chemin porte `:notebookId` (le harnais l'impose, voir ci-dessous) ; elle s'exécute après `AccessTokenGuard` (globale → 401 d'abord). Carnet d'autrui, inexistant, supprimé ou identifiant mal formé → **même 404** « Carnet introuvable » (pas 403 : l'existence ne fuit pas). Les ressources filles (dépenses…) devront en plus être filtrées par `notebook_id` dans leurs requêtes.
- **Routes** : `GET /api/v1/notebooks` (carnets accessibles, triés par création, `{ id, name, kind, role }`, `no-store`) et `GET /api/v1/notebooks/{notebookId}`.
- **Harnais** (`test/support/access.ts`, `test/access/cross-tenant.spec.ts`) : parcourt toutes les routes de l'OpenAPI hors liste blanche publique exacte (`test/support/public-routes.ts`, partagée avec `public-routes.spec.ts`). Toute route doit être soit de carnet (`{notebookId}` dans le chemin : B reçoit 404 avec le carnet de A, corps identique à un carnet inexistant hors `instance`, données de A inchangées ; A passe la garde ; si la route a d'autres paramètres, B les vise aussi via **son propre** carnet → 404, seul le filtre `notebook_id` de la route protégeant alors A), soit listée comme route de compte (la réponse faite à B ne contient ni l'id, ni l'adresse, ni le carnet de A). Dans les deux cas, la ligne `user` et les carnets de A sont relus inchangés. Limite : une route exclue de l'OpenAPI (`@ApiExclude*`) échappe au harnais. Une route nouvelle non classée, ou un paramètre de chemin inconnu du harnais (ex. `{expenseId}`), fait échouer le test : fournir alors le corps valide (`BODIES`) et la ressource de A (`RESOURCE_PARAMS`), et compléter le contrôle « inchangé » par les tables concernées.
- `test/support/users.ts › createUser` crée aussi le carnet personnel (`notebookId`), comme un vrai compte.

## ADR-022 — Profil `GET/PATCH /me` : préférences modifiables, fuseau IANA, devise ; `@depenseo/shared` compilé (2026-11-04)

Contexte : §8.3 liste pour l'utilisateur « langue, fuseau horaire, devise, … dates de consentement » ; NF-FMT-04 calcule les périodes dans le fuseau de l'utilisateur. Le cahier ne précise ni le format du fuseau, ni si les consentements sont modifiables. Premier import de `@depenseo/shared` dans l'API.

- **Lecture** `GET /api/v1/me` → `{ id, email, language, timeZone, currency, termsAcceptedAt, privacyAcceptedAt }` (dates ISO 8601 UTC ou `null`), `no-store`.
- **Modification** `PATCH /api/v1/me` : objet zod **strict**, champs optionnels `language` (`fr`|`en`), `timeZone`, `currency` ; au moins un champ ; clé inconnue (adresse, rôle, plan, consentements…) → 400 sans rien modifier. Renvoie le profil relu, `updated_at` = horloge applicative. Pas de verrou ni de transaction : un seul `UPDATE` par champs fournis (dernier écrit gagne).
- **Consentements en lecture seule** : posés à l'inscription (CGU + confidentialité, une seule case, ADR-017). Une ré-acceptation après changement de CGU sera traitée si une version de CGU apparaît (hors MVP).
- **Fuseau** (`packages/shared/src/time-zone.ts › normalizeTimeZone`) : forme `Zone/Lieu[/…]` ou `UTC` (casse libre), ≤ 64 caractères, **et** reconnu par Temporal (`temporal-polyfill`, comme les calculs de période). Stocké en casse exacte (`europe/paris` → `Europe/Paris`, `us/eastern` → `US/Eastern`) **sans canonicalisation** : `Intl…resolvedOptions()` remplacerait `America/Montreal` par `America/Toronto` (et le résultat varie selon l'ICU), Temporal ne normalise que la casse.

Vitest de l'API résout le paquet vers ses sources par `resolve.alias` (pas de build préalable pour les tests).

Le déploiement Passenger (P7) devra embarquer `packages/shared/dist`.

## ADR-023 — Catégories : plan par défaut copié par carnet, deux niveaux, masquage, suppression logique des seules personnalisées (2026-11-04)

Contexte : F-CAT-01/02 et §8.3 (« catégorie (nom, icône, couleur, parent) ») ne fixent ni les sous-catégories, ni les icônes/couleurs, ni la profondeur, ni le sort d'une catégorie supprimée.

- **Table `category`** (migration 0004) : `notebook_id`, `parent_id` (NULL = racine), `system_key` (clé stable du plan, ex. `housing.rent`, unique par carnet ; NULL = personnalisée), `name` varchar(100), `icon` varchar(32) (emoji utf8mb4 ou nom d'icône), `color` `#RRGGBB` majuscules, `position` (ordre ; personnalisées 1000), `hidden`, horodatages, `deleted_at`, index de synchronisation `(notebook_id, updated_at, id)`. FK `parent_id` en cascade (seule la suppression physique d'un carnet l'exerce).
- **Plan par défaut** (`src/categories/default-plan.ts`) : 14 racines du cahier des charges, 2 à 5 sous-catégories chacune, emoji et couleur par racine (héritées par les sous-catégories). Copié dans chaque carnet par `createPersonalNotebook`, dans la même transaction, **dans la langue du compte** à cet instant (fr/en) : les libellés deviennent des données de l'utilisateur, ils ne suivent pas un changement de langue ultérieur (option la plus simple ; `system_key` permet une traduction côté client plus tard).
- **Deux niveaux** : un parent doit être une racine active du même carnet, différente de la catégorie ; une catégorie qui a des enfants actifs ne peut pas devenir sous-catégorie. Parent inconnu, d'un autre carnet, ou sous-catégorie → même **422** (pas de fuite). Les écritures verrouillent la ligne `notebook` (`FOR UPDATE`) pour sérialiser les changements de hiérarchie.
- **Routes** `/notebooks/{notebookId}/categories[/{categoryId}]` : `GET` (actives : non supprimées, non masquées, parent non masqué ; `?includeHidden=true` : toutes les non supprimées), `POST` (corps strict `{id UUID v7, name, icon, color, parentId?}` ; idempotent : un rejeu renvoie 201 et la ligne existante, la première écriture gagne ; identifiant d'un autre carnet ou supprimé → 409), `GET /{id}` (y compris masquée), `PATCH` (`name`, `icon`, `color`, `parentId`, `hidden` ; aussi pour le plan par défaut), `DELETE` (204, idempotent sur une catégorie déjà supprimée).
- **Masquage vs suppression** : une catégorie du plan ne se supprime pas (409, on la masque) ; une personnalisée avec sous-catégories actives non plus (409). Suppression = logique : la ligne reste pour les dépenses qui la référencent et pour la synchronisation. Une catégorie masquée reste valide pour une dépense (à tester en P2-02).
- Une racine masquée reste un parent valide : la sous-catégorie créée dessous est alors absente des listes actives (cohérent avec le masquage du sous-arbre). `includeHidden` n'accepte que `true`/`false` (sinon 400).
- Le 409 sur un identifiant pris dans un autre carnet révèle qu'un UUID existe ailleurs : négligeable (UUID v7 de 74 bits aléatoires, non énumérables), accepté.
- Propriétaire et membre ont les mêmes droits (partage hors MVP).

## ADR-024 — Dépenses : montant strictement positif, devise par défaut du compte, étiquettes par nom, restauration explicite (2026-11-04)

Contexte : F-DEP-03/10, NF-OFF-01, NF-FMT-01/02 et le modèle « Expense » du §8.3 ne fixent ni les bornes du montant, ni les longueurs de texte, ni l'identité d'une étiquette, ni la forme de l'annulation.

- **Tables** (migration 0005) : `expense` (`amount` BIGINT centimes, `currency` CHAR(3), `category_id`, `spent_on` DATE lue en chaîne, `note` varchar(500), `merchant` varchar(100), `source` varchar(16) `manual`|`recurrence`, horodatages, `deleted_at`, index `(notebook_id, updated_at, id)` et `(notebook_id, spent_on, id)`) ; `tag` (`name` varchar(50), unique `(notebook_id, name)`, synchronisée) ; `expense_tag` (clé `id` + unique `(expense_id, tag_id)` (invariant « clé primaire `id` »), sans `notebook_id` : elle voyage avec sa dépense, dont `updated_at` avance à chaque changement d'étiquettes — P2-04 l'exposera dans la dépense). FK `notebook_id` et `expense_id` en cascade ; FK `expense.category_id` et `expense_tag.tag_id` **sans cascade** : une purge de catégorie ou d'étiquette (P2-04) échoue bruyamment (1451) au lieu d'effacer des dépenses ou des liaisons en silence. Conséquence : un `DELETE notebook` direct est refusé tant qu'il reste des dépenses ; la suppression physique passe par `purgeNotebook(tx, id)` (`src/notebooks/purge-notebook.ts`, dépenses d'abord), à utiliser par P4-06.
- **Montant** : entier JSON strictement positif, ≤ 99 999 999 999 unités mineures ; décimal, chaîne, 0 ou négatif → 400. Un remboursement (montant « remboursée liée » du §8.3) est hors MVP.
- **Devise** : facultative, défaut = devise du compte à la création (multi-devises, montant converti et moyen de paiement du §8.3 : hors MVP, colonnes non créées). Code hors `SUPPORTED_CURRENCIES` → 400.
- **Catégorie** obligatoire, non supprimée, du même carnet ; masquée acceptée (ADR-023). Sinon **422** (inconnue, autre carnet, supprimée : même réponse).
- **Note / marchand / étiquettes** : espaces de bord retirés, forme NFC ; note ou marchand vide → NULL.
- **Étiquettes** : liste de noms (≤ 10, 1 à 50 caractères) ; identité = nom dans le carnet **à la collation près** (`Été` = `ete` sous utf8mb4_unicode_520_ci), le premier nom enregistré fait foi ; créées à la volée par le serveur (`INSERT … ON DUPLICATE KEY UPDATE`), identifiant serveur (le nom est la clé naturelle, deux clients hors ligne convergent). Un `PATCH tags` remplace la liste. Pas de route de gestion des étiquettes au MVP (ni renommage ni suppression) ; si une étiquette est un jour supprimée logiquement, sa réutilisation devra la réactiver (`deleted_at = NULL`, `updated_at` avancé).
- **`source`** fixé par le serveur (`manual` via l'API ; `recurrence` par P4-02) ; absent des corps (objets stricts).
- **Idempotence** : comme ADR-023 (rejeu → 201 et ligne existante, la première écriture gagne ; identifiant d'un autre carnet → 409). Rejeu d'une création **supprimée** → 409 avec un `detail` distinct (« la restaurer ») : pas de résurrection silencieuse, la restauration est explicite. La restauration ne revérifie pas la catégorie : supprimée entre-temps, elle reste référencée (comme pour une dépense active, ADR-023).
- **Suppression / annulation (F-DEP-10)** : `DELETE` logique (204, idempotent), `POST /expenses/{id}/restore` (200, sans effet sur une dépense active ; 404 si inconnue). Pas de limite de 5 s côté serveur : la fenêtre d'annulation est une affaire d'interface, la restauration reste possible jusqu'à la purge (P2-04).
- Les écritures verrouillent la ligne `notebook` (`lockNotebook`, extrait de P2-01) : catégorie supprimée en parallèle, étiquettes créées en parallèle, futures alertes de limite (P3-03) sérialisées.
- La liste des dépenses (`GET /expenses`) est livrée avec la recherche et la pagination (P2-03).

## ADR-025 — Liste et recherche des dépenses : filtres stricts, tri par date, curseur par clé (2026-11-04)

Contexte : F-DEP-09 et §8.1 (recherche insensible à la casse et aux accents) ne fixent ni l'ordre de la liste, ni la pagination, ni la forme des filtres.

- **Route** : `GET /notebooks/{id}/expenses` → `{ items, nextCursor }` ; dépenses **actives** seulement (les supprimées passent par la synchronisation, P2-04).
- **Tri** : `spent_on` décroissant puis `id` décroissant (UUID v7 : ordre de création à date égale) ; servi par l'index `(notebook_id, spent_on, id)`.
- **Pagination par clé** : curseur opaque = base64url de `AAAA-MM-JJ~uuid` de la dernière ligne ; condition `spent_on < d OR (spent_on = d AND id < i)`. Lecture de `limit + 1` lignes : `nextCursor` est `null` dès qu'il n'y a plus rien (jamais de page vide). Taille 1–100, défaut 50. Le curseur ne porte pas les filtres : au client de les renvoyer à l'identique.
- **Texte `q`** (≤ 100 caractères, espaces retirés, NFC, vide = pas de filtre) : `LIKE '%…%'` sur `note` **ou** `merchant`, jokers `%`/`_` échappés (caractère d'échappement `!`, pas `\` qui dépend de `NO_BACKSLASH_ESCAPES`). L'insensibilité casse/accents vient de la collation utf8mb4_unicode_520_ci des colonnes, pas d'un traitement applicatif. Les étiquettes ne sont pas cherchées (filtre par étiquette hors F-DEP-09, à ajouter si besoin). Pas d'index plein texte : parcours du carnet, acceptable aux volumes d'un carnet personnel (NF-PERF-02 à surveiller).
- **Montant** `minAmount`/`maxAmount` : entiers en unités mineures, bornes incluses, sans tenir compte de la devise (mono-devise au MVP, ADR-024). **Période** `from`/`to` : dates calendaires incluses. min > max ou from > to → 400.
- **Catégories** `categoryId` (répétable, ≤ 50) : correspondance **exacte**, une catégorie parente n'inclut pas ses sous-catégories (au client d'envoyer la liste ; option la plus simple). Catégorie inconnue ou d'un autre carnet : aucun résultat, pas d'erreur.
- **Validation** : `parseQuery(schema, query)` (`src/http/parse-query.ts`), objet strict : paramètre inconnu, paramètre simple répété, nombre non entier (chiffres seuls), date impossible, curseur illisible → 400 « Paramètres invalides : … » sans valeur reçue.

## ADR-026 — Synchronisation différentielle par carnet et purge des suppressions (2026-11-04)

Contexte : §8.2 et NF-OFF-01 fixent le curseur `(updated_at, id)`, l'inclusion des suppressions logiques et leur purge après 30 jours, mais ni le chemin, ni le format, ni la reprise d'un appareil resté longtemps hors ligne.

- **Route** : `GET /notebooks/{id}/sync?updated_since=&cursor=&limit=` (garde de carnet, comme toute ressource de carnet). Réponse `{ categories, tags, expenses, nextCursor, nextUpdatedSince }` ; les lignes supprimées sont incluses avec `deletedAt` non nul, les catégories masquées aussi.
- **Ordre** : un seul flux paginé parcourant catégories, puis étiquettes, puis dépenses, chaque table triée par `(updated_at, id)` croissants via l'index `(notebook_id, updated_at, id)`. `limit` (1–500, défaut 200) compte les lignes des trois tables. Curseur opaque base64url (`v1~table~updated_at ms~id~since~watermark`) ; `updated_since` et `cursor` sont exclusifs (400).
- **Pas d'instantané commun** aux pages d'un parcours : une catégorie ou une étiquette créée après le passage de sa table n'arrive qu'au parcours suivant, alors qu'une dépense qui la référence peut arriver dans le parcours en cours. Le client (P6-05) **doit tolérer une référence pendante** jusqu'au parcours suivant (pas de FK stricte côté Drift sur `category_id`, ou contrôle différé). L'ordre catégories → étiquettes → dépenses réduit seulement la fréquence du cas.
- **Filigrane** : `nextUpdatedSince` = horloge du serveur au **premier** appel du parcours moins 5 minutes, porté par le curseur et identique sur toutes les pages. Les horodatages sont fournis par l'application avant la validation de la transaction : une écriture validée en retard (attente de verrou ≤ 50 s, rejeu sur interblocage) garde un `updated_at` antérieur à sa visibilité ; la marge de 5 minutes la rattrape au parcours suivant. Le client rejoue donc parfois quelques lignes déjà reçues (application idempotente par `id`, dernière version reçue gagne). `updated_since` est inclusif (`>=`).
- **Appareil hors ligne trop longtemps** : `updated_since` antérieur à maintenant − 29 jours → **410** ; le client refait une synchronisation complète (sans `updated_since`). Un jour de marge sous la rétention de 30 jours : une suppression ne peut pas être purgée avant d'avoir été servie à un client accepté. Contrôle fait au premier appel seulement : un curseur repris très tard n'est pas refusé, le 410 tombe alors au parcours suivant. Un `updated_since` dans le futur est accepté (page vide, filigrane antérieur).
- **Étiquettes d'une dépense** : la dépense porte ses noms d'étiquettes (comme `GET …/expenses`) ; `expense_tag` n'est pas synchronisée seule (ADR-024 : `updated_at` de la dépense avance à chaque changement d'étiquettes).
- **Purge** (`purge-deleted-sync-rows`, tâche périodique du cron) : supprime physiquement, par lots, les dépenses supprimées depuis plus de 30 jours (liaisons d'étiquettes en cascade), puis les étiquettes et catégories supprimées depuis plus de 30 jours **non référencées** (aucune liaison, aucune dépense même supprimée, aucune sous-catégorie même supprimée : la FK `parent_id` est en cascade et ne doit jamais emporter une sous-catégorie vivante). Sélection des candidats puis suppression par identifiants avec revérification de la référence (MySQL 8 refuse une sous-requête sur la table supprimée). La FK sans cascade (ADR-024) reste le filet de sécurité. Index `(deleted_at)` sur `expense`, `tag`, `category` (migration 0006) : la purge parcourt toutes les instances à chaque passage du cron.
- Hors périmètre : purge immédiate à la suppression du compte (F-AUTH-07, P4-06).

## ADR-027 — Limite globale : versions datées du jour, une par jour, historique immuable (2026-11-05)

- **Modèle** (`spending_limit`, migration 0007) : chaque ligne est une **version** (période `month`/`week`, jour de début, montant, devise, `include_recurring`, date d'effet). `amount` NULL = « aucune limite » : la suppression (F-LIM-01 « facultative ») est une nouvelle version sans montant, l'historique antérieur reste (F-LIM-09). Devise = devise du compte à la création (mono-devise, ADR-024 ; non fournie par le client).
- **Unicité** : index unique `(notebook_id, category_key, effective_date)`, `category_key` = colonne générée stockée `coalesce(category_id, 16 octets nuls)` (§8.2). Écart assumé avec §8.2 qui cite aussi la période : une seule limite globale à la fois (« mensuelle ou hebdomadaire au choix ») ; le type de période est un attribut de la version, pas une clé. Pas de `NOT NULL` sur la colonne générée (refusé par MariaDB). `category_id` toujours NULL au MVP (limites par catégorie : F-LIM-07, backlog) ; l'API ne l'accepte pas.
- **Date d'effet** : calculée par le serveur = aujourd'hui dans le fuseau du compte (NF-FMT-04), jamais fournie par le client (empêche de réécrire le passé). Deux créations le même jour → **409** ; le client modifie alors la version du jour par `PATCH`. Une version d'un jour passé n'est plus modifiable (409) : elle appartient à l'historique. Date du jour antérieure à la dernière date d'effet (fuseau changé vers l'ouest, horloge reculée) → 409 : l'historique ne s'insère jamais avant la dernière version (la version « de demain » n'est alors modifiable qu'une fois ce jour arrivé, cas rare accepté).
- **Premier jour couvert et version en vigueur** (`withAppliesFrom`/`versionInForce`, `src/limits/limit-history.ts`) : une version s'applique dès le début de la période **en cours** à sa date d'effet `e`, soit le plus tardif de : début de sa propre période contenant `e`, début de la période de la version précédente contenant `e`, premier jour de la version précédente. Changer le montant le 15 mars vaut pour tout mars ; changer les règles (mois → semaine, jour de début) ne fait **jamais** basculer une période terminée sous la nouvelle limite (la première période de la nouvelle version **et** la dernière de la précédente peuvent alors être tronquées, ex. mois → semaine le 18 mars : l'ancienne couvre du 1er au 15 mars ; P3-02 calcule jauge et totaux sur ces périodes partielles). À une date donnée, la version en vigueur est la plus récente dont le premier jour est passé. `appliesFrom` est exposé par `GET …/limits` ; il n'est pas dans la sync (il dépend des versions précédentes, une page peut n'en contenir qu'une partie) : le mobile affiche la jauge calculée par l'API (P3-02) et peut relire `GET …/limits`.
- **Insertion sans `ON DUPLICATE KEY UPDATE`** (écart à l'invariant 5, justifié) : un IODKU avalerait en silence le conflit sur l'index unique secondaire (même jour) au lieu du 409 attendu. Le rejeu par UUID est traité en amont (lecture sous verrou du carnet) ; un `ER_DUP_ENTRY` résiduel → 409.
- **Routes** : `GET/POST /notebooks/{id}/limits`, `PATCH /notebooks/{id}/limits/{limitId}`. Rejeu du même UUID → 201 et version existante ; UUID d'un autre carnet → 409. Pas de route de suppression d'une version (inutile : suppression = version sans montant) : `deleted_at` existe pour l'invariant de synchronisation, sans purge. F-LIM-07 (backlog) : la purge des catégories (ADR-026) devra vérifier `spending_limit.category_id` (FK sans cascade).
- **Synchronisation** : `limits` ajouté **en fin** de `SYNC_TABLES` (les curseurs émis gardent leur index).
- **Premium** (§ offre) : « historique des limites » Premium vs F-LIM-09 (M) : l'historique est toujours conservé et sert aux calculs ; seul son affichage pourra être réservé au Premium (P6).

## ADR-028 — Jauge de limite : périodes tronquées, rythme en jours entiers, mono-devise (2026-11-05)

- **Route** : `GET /notebooks/{notebookId}/limits/current?past=N` (et non `/limits/current` sans carnet, comme le libellé de P3-02) : la limite appartient au carnet (ADR-021/027), la garde de carnet et le harnais d'isolement s'appliquent sans exception. `past` = nombre de périodes précédentes (0–24, défaut 0 ; le tableau de bord P3-05 en demandera 12). Réponse `{timeZone, today, current, past[]}` (passées : plus récente d'abord).
- **« Aujourd'hui »** = `todayIn(fuseau du compte qui consulte)` (NF-FMT-04) ; carnet personnel au MVP, donc fuseau du propriétaire. Partage de carnet (backlog) : chaque membre verra la jauge dans son fuseau.
- **Découpage** (`periodSlices`, `src/limits/period-summary.ts`) : la période contenant `today` suit la règle de la version en vigueur (ADR-027), bornée à gauche par son `appliesFrom` et à droite par la veille du `appliesFrom` de la version suivante ; on remonte de veille en veille. Avant la première version : règle de cette première version (ou mois civil s'il n'y en a aucune), sans limite. Une période tronquée (changement de règles) est une période à part entière : jauge, rythme et totaux portent sur ses seuls jours. Une version « de demain » (fuseau vers l'ouest, ADR-027) dont le premier jour couvert est déjà passé est en vigueur dès aujourd'hui, avant sa date d'effet (même règle que `versionInForce`).
- **Dépensé** : somme des dépenses non supprimées du carnet dont `spent_on` est dans la période, **y compris les dates futures** de la période en cours (une dépense saisie à l'avance compte dans sa période). Les dépenses de récurrence ne sont créées qu'à l'échéance par le cron (P4-02) : pas de gonflement anticipé ; les échéances à venir relèvent des projections (P3-05/P4), pas du dépensé. Récurrences (`source = recurrence`) exclues si la version en vigueur sur la période a `include_recurring = false` (F-LIM-05) ; sans version, incluses. Une seule requête `SUM … GROUP BY (spent_on, source, currency)` sur toute la plage, agrégée en `bigint` côté API ; total au-delà de 2^53 → erreur 500 plutôt qu'un arrondi.
- **Devise** : devise de la version (ou du compte sans limite). Les dépenses d'une autre devise ne sont ni converties ni comptées (multidevise hors MVP) ; elles sont signalées par `otherCurrencies` pour que l'interface puisse l'indiquer.
- **Restant** = limite − dépensé (négatif en cas de dépassement). **Rythme** : `consumedPercent = ⌊100 × dépensé / limite⌋` (peut dépasser 100) et `elapsedPercent = ⌊100 × jours écoulés / jours de la période⌋`, jours écoulés **aujourd'hui compris** (1er jour d'un mois de 31 jours → 3 %) ; 100 % pour une période passée. Comptés en jours calendaires (pas en heures) : insensible aux changements d'heure. `limit`, `remaining`, `consumedPercent` = NULL sans limite (ou version sans montant). Les jours bruts (`elapsedDays`, `totalDays`) sont fournis pour l'affichage.

## ADR-029 — Détection des alertes de limite (2026-11-05)

Contexte : P3-03 (F-LIM-04, F-NOT-01, ADR-004) demande une alerte par seuil et par période, idempotente par la clé `limit:<carnet>:<période>:<seuil>`. Or les tâches terminées sont purgées après 7 jours (ADR-016) : la clé d'unicité de `job` seule ne protège pas toute une période mensuelle.
Décision :
- Détection après chaque création, modification et restauration de dépense, dans la transaction d'écriture (carnet verrouillé) ; pas après une suppression (le total baisse). Une création rejouée (idempotente) ne relance rien.
- Seule la **période en cours** (aujourd'hui dans le fuseau du compte auteur de l'écriture) est évaluée, avec la limite globale en vigueur (règles de `summarize`, ADR-028 : récurrences exclues si la limite le dit, autres devises ignorées). Une dépense saisie dans une période passée n'alerte pas.
- Seuils plafonnés à **200 %** (`MAX_ALERT_PERCENT`) : 80, 100, 110 … 200, soit au plus 12 alertes par période, même avec une très petite limite (sans plafond, chaque tranche de 10 % au-delà de 1 000 % alerterait encore).
- Seul le **plus haut seuil atteint** est notifié (saut de 0 à 135 % → une alerte « 130 % », pas cinq), et seulement s'il dépasse le dernier seuil notifié pour la période, mémorisé dans la table `limit_alert (notebook_id, period_start, threshold)` (migration 0008, non synchronisée). Repasser sous un seuil puis le refranchir n'alerte pas.
- Tâche `notify`, charge utile `{kind: 'limit', notebookId, periodStart, threshold}` (union discriminée par `kind`, réutilisée en P3-04 et P4), clé `limit:<carnet>:<début de période>:<seuil>`. Aucun gestionnaire n'est enregistré avant P4-04 : les tâches restent `pending` jusque-là ; le gestionnaire de P4-04 devra ignorer une alerte dont la période n'est plus en cours (sinon envoi groupé d'alertes périmées au déploiement).
- `limit_alert` porte `deleted_at` et l'index de synchronisation pour satisfaire l'invariant des tables de carnet (test d'invariants), sans être synchronisée ni supprimée logiquement.
- Un changement de limite qui fait franchir un seuil sans nouvelle dépense n'alerte pas (F-LIM-04 vise les dépenses) ; la période tronquée par une nouvelle version a son propre début, donc ses propres seuils : une nouvelle version en cours de mois peut donner une seconde alerte « 80 % » dans le même mois civil (assumé : la limite a changé).
Conséquence : nombre d'alertes borné par période, idempotence durable indépendante de la purge des tâches.

## ADR-030 — Détection de la dépense inhabituelle (2026-11-05)

Contexte : P3-04 applique ADR-005 (≥ 3 × médiane de la catégorie racine sur 90 jours, ≥ 5 dépenses d'historique, ≥ 20 €) ; plusieurs points restent ouverts.
Décision :
- Détection à la **création** seulement (`ExpensesService.create`, dans la transaction, carnet verrouillé) ; ni la modification ni la restauration ne déclenchent (une correction de montant n'est pas une nouvelle dépense). Clé de tâche `unusual:<dépense>` : un rejeu n'alerte jamais deux fois.
- Historique = dépenses actives du carnet dont la catégorie est la racine ou l'une de ses sous-catégories, **même devise** que la dépense, datées de J−90 à J inclus, soit 91 jours avec les autres dépenses du même jour (lecture la plus simple des « 90 jours précédents » d'ADR-005 ; J = date de la dépense, pas aujourd'hui), toutes sources (manuelles et récurrentes), la dépense elle-même exclue. Une dépense antidatée est donc comparée à son propre passé.
- Les dépenses générées par une récurrence (P4-02) ne déclenchent **pas** la détection : leur montant est attendu (fixe ou estimé) et déjà annoncé par l'échéance ; elles comptent en revanche dans l'historique.
- Médiane paire = moyenne des deux valeurs centrales, comparée en entiers (2 × montant ≥ 3 × (a + b)).
- Plancher de 2 000 unités mineures **dans la devise de la dépense**, sans conversion (devises multiples hors MVP) : approximation acceptée pour les devises non euro.
- Charge utile `notify` `{kind: 'unusual_expense', notebookId, expenseId}`, sans montant (ADR-003) ; `NOTIFY` déplacé dans `src/notifications/notify-job.ts`.
Conséquence : une requête indexée `(notebook_id, spent_on)` par création ; le gestionnaire push (P4-04) relira la dépense (et ignorera une dépense supprimée entre-temps).

## ADR-031 — Tableau de bord (2026-11-05)

Contexte : P3-05 (F-TB-01/02) ; le cahier ne précise ni la route, ni le nombre de dernières dépenses, ni le niveau de la répartition, ni la devise des graphiques ; les récurrences n'existent pas encore.
Décision :
- Route `GET /notebooks/{notebookId}/dashboard` (convention des routes de carnet, garde de carnet), et non `/dashboard`. « Aujourd'hui » dans le fuseau du compte qui consulte (comme la jauge, ADR-028).
- `gauge` = résumé de la période en cours (`summarize`) : `limit` NULL ⇒ « total dépensé sans limite ».
- `evolution` = 12 périodes (en cours d'abord, découpage ADR-027), `evolution[0]` = `gauge`.
- Toutes les sommes suivent les règles de comptage de la jauge (`sliceScope`) : devise de la version (du compte sans limite), récurrences exclues si la version les exclut ; les autres devises sont ignorées et signalées par `gauge.otherCurrencies`. La somme de la répartition égale `gauge.spent`.
- `categories` : répartition de la période en cours par **catégorie racine** (une dépense sur une sous-catégorie compte pour sa racine), total décroissant puis identifiant, `percent` = ⌊100 × part⌋ calculé par l'API (invariant 8).
- `cumulative.current` : un point par jour de début de période à aujourd'hui (une dépense datée plus tard dans la période figure dans la jauge mais pas encore dans le cumul) ; `cumulative.previous` : période précédente entière. Axe commun = rang du jour (`day`), les deux périodes pouvant différer en longueur.
- `recent` : 5 dernières dépenses actives, par date puis identifiant décroissants (même tri que la liste, ADR-025).
- `upcoming` (prochaines échéances) reporté à P4-01, où les récurrences sont créées (champ ajouté sans rupture du contrat).
- Chaque période compte dans la devise de **sa** version : si une nouvelle version change de devise, cumul courant et précédent sont en devises différentes (multidevise hors MVP ; la devise de chaque période figure dans `evolution`).
Conséquence : 5 requêtes par appel (compte, versions, totaux journaliers sur 12 périodes, totaux par racine, dernières dépenses), sans cache ni transaction : sous READ COMMITTED, une écriture concurrente peut rendre momentanément Σ `categories` ≠ `gauge.spent` (corrigé à l'appel suivant).

## ADR-032 — Dépenses récurrentes et échéances (2026-11-05)

Contexte : P4-01 (F-REC-01/03, F-TB-01) ; le cahier ne précise ni la forme du « jour », ni la génération des échéances, ni les routes des actions, ni le comportement d'une modification de calendrier.
Décision :
- Tables `recurring_expense` et `occurrence` (migration 0009), synchronisées (`recurringExpenses` puis `occurrences` en fin de `SYNC_TABLES`). Routes `…/notebooks/{id}/recurring-expenses[/{recurringId}[/occurrences]]` et `…/notebooks/{id}/occurrences/{occurrenceId}` (`PATCH` = ajuster, `POST …/pay`, `POST …/skip`), convention des routes de carnet.
- Le « jour » est celui de la **date de départ** (`startDate` = première échéance) : jour de semaine (hebdomadaire) ou du mois. La n-ième échéance = départ + n × pas (7 j, 1/3/12 mois) avec repli en fin de mois, **jamais** par chaînage : 31/01 → 28/02 → 31/03 ; trimestriel 31/01 → 30/04 → 31/07 → 31/10 ; 29/02 → 28/02 hors années bissextiles. `ponctuelle` = une seule échéance.
- Fréquence et date de départ **immuables** (clé inconnue au PATCH → 400) : changer de calendrier = supprimer puis recréer. Modifiables : nom, montant, `amountKind` (`fixed`|`estimated`), catégorie, mode (`auto`|`confirm`, défaut `confirm`). Devise = celle du compte par défaut.
- Échéances **matérialisées** jusqu'à un horizon glissant de 40 jours (`generated_through`, interne), et toujours au moins la prochaine (trimestrielle, annuelle) ; une ponctuelle passée marque la récurrence épuisée (`9999-12-31`). Création : à partir d'**aujourd'hui dans le fuseau du compte** (une date de départ passée ne crée aucune échéance passée ; une ponctuelle passée → 422). Tâche périodique `generate-occurrences` : avance l'horizon (date UTC, l'écart de fuseau est absorbé par la marge), sous verrou du carnet puis de la récurrence (même ordre que les services). Unicité `(récurrence, date)`.
- Montant d'une échéance : `occurrence.amount` NULL = montant de la récurrence (suit ses modifications) ; ajusté ou payé = valeur propre. API : `amount` effectif + `adjusted` ; sync : colonne brute.
- Payer : crée la dépense (`source = recurrence`, catégorie et devise de la récurrence, nom en note, date = échéance par défaut, identifiant client `expenseId`) dans la même transaction, vérifie les alertes de limite, pas la détection de dépense inhabituelle (ADR-030). Rejeu avec la même `expenseId` → 200 ; autre `expenseId` sur une échéance payée, ou échéance sautée → 409 (après purge de la dépense, `expense_id` est NULL : un rejeu donne alors 409, accepté). Sauter : idempotent ; pas d'annulation au MVP. Supprimer la dépense ensuite ne rouvre pas l'échéance.
- Supprimer une récurrence : suppression logique de la récurrence et de **toutes** ses échéances (chaque client reçoit leur suppression avant la purge physique) ; l'historique reste porté par les dépenses `source = recurrence`. Purge (ADR-026) : récurrences supprimées depuis 30 jours (échéances en cascade) avant les catégories ; une catégorie référencée par une récurrence, même supprimée, n'est pas purgée. Supprimer une catégorie utilisée par une récurrence active → 409 (sinon ses échéances ne pourraient plus être payées). `occurrence.expense_id` : `ON DELETE SET NULL` à la purge des dépenses, sans avancer `updated_at` (le client garde un identifiant de dépense déjà supprimée, sans effet).
- Tableau de bord (ADR-031) : `upcoming` = 5 échéances en attente dues d'ici 31 jours, en retard comprises (`overdue` calculé par l'API, fuseau du compte), par date puis identifiant.
- Colonne `pricing` (et non `amount_kind`) : la règle `*amount*` = BIGINT du test d'invariants.
Conséquence : P4-02 traitera les échéances dues (mode auto → `pay` interne idempotent par échéance) ; P4-03 ajoutera les réglages de rappel à `recurring_expense`. Pas d'annulation de « sauter », pas de modification de calendrier (recréer).

## ADR-033 — Échéances dues traitées par le cron (2026-11-05)

Contexte : P4-02 (F-REC-02) ; le cahier dit seulement « enregistrement automatique ou demande de confirmation » ; ni statut « à confirmer », ni heure de déclenchement.
Décision :
- Tâche périodique `process-due-occurrences` (`src/recurring/due-occurrences.ts`) : une échéance `pending` est **due** quand `due_date ≤ aujourd'hui` dans le fuseau du **propriétaire du carnet** (`user.time_zone`), donc à minuit heure locale. Pré-filtre SQL `due_date ≤ lendemain UTC`, pagination par `(due_date, id)` (les échéances pas encore dues localement ne bouclent pas), index `occurrence_due_idx (status, confirmation_requested_at, due_date)` (migration 0010).
- Chaque échéance est traitée dans sa transaction, sous verrou du carnet, statut relu : deux passages (ou deux crons concurrents) → un seul traitement.
- Mode `auto` : `payOccurrence` (partagé avec `POST …/pay`) crée la dépense `source = recurrence` au montant attendu (ajusté sinon celui de la récurrence), datée de l'échéance, `expenseId` v7 généré côté serveur ; alertes de limite vérifiées (propriétaire), pas de détection inhabituelle (ADR-030). Si la catégorie n'est plus utilisable, repli sur le mode confirmation.
- Mode `confirm` : « à confirmer » n'est **pas** un nouveau statut (pay/skip/adjust et le tableau de bord restent inchangés) mais la colonne `confirmation_requested_at` (exposée en sync ; `awaitingConfirmation` dans les vues d'échéance), plus une tâche `notify` `{kind:'occurrence_due', notebookId, occurrenceId}` de clé `occurrence-due:<id>` (§8.2 cite `occurrence:<id>` ; préfixe par type pour ne pas entrer en collision avec les rappels J-3/jour J de P4-03), sans montant. La colonne, durable, empêche une seconde notification après la purge des tâches (7 j).
- Une échéance en échec (fuseau invalide, erreur durable) n'arrête pas le passage : les autres sont traitées, puis la tâche lève une `ScheduledTaskError` (détails structurés `failed`, `occurrenceId`, journalisés par `jobs-run` ; jamais de montant). `runScheduledTasks` isole désormais chaque tâche périodique : un échec est rendu dans `failures` et n'empêche ni les tâches suivantes ni `runJobs` (code de sortie 1). Une échéance en échec durable est retentée à chaque passage : le seul cas connu, un fuseau invalide, est exclu à l'écriture (`normalizeTimeZone`, ADR-022).
- Les échéances en retard d'avant la mise en service sont traitées au premier passage (la création ne génère jamais d'échéance passée, ADR-032).
Conséquences : le gestionnaire `notify` (P4-04) doit ignorer une échéance déjà payée ou sautée entre-temps (et un carnet supprimé). L'application mobile (P6-09) affiche « à confirmer » à partir de `confirmationRequestedAt` ; en mode auto, elle ne propose pas « payer » sur une échéance déjà due et traite le 409 `NOT_PENDING` (paiement hors ligne doublé par le cron). Après repli pour catégorie inutilisable, `POST …/pay` répond 422 : l'utilisateur ne peut que sauter l'échéance (choix d'une autre catégorie au paiement : non prévu au MVP). Passage non borné en durée : un gros rattrapage peut dépasser 50 s (à surveiller, cf. §8.2).

## ADR-034 — Rappels d'échéance et rappel quotidien de saisie (2026-11-05)

Contexte : P4-03 (F-REC-04, F-NOT-02, NF-FMT-05). Le cahier dit « rappels configurables (J-3, jour J) à l'heure locale de l'utilisateur » et « rappel quotidien facultatif, à l'heure choisie », sans heure par défaut ni règle de rattrapage ; le plan précise « réglables par récurrence ».
Décision :
- Réglages : `recurring_expense.remind_three_days_before` et `remind_on_due_date` (booléens, vrais par défaut, modifiables par `POST`/`PATCH` et exposés en sync) ; `user.reminder_time` (`HH:MM`, défaut **09:00**, une heure commune à tous les rappels d'échéance du compte) et `user.daily_reminder_time` (`HH:MM`, NULL = désactivé, défaut désactivé), modifiables par `PATCH /me`. Heures en `CHAR(5)` validées `00:00`–`23:59` (migration 0011).
- Interprétation locale (`src/notifications/reminder-time.ts`) : `PlainDateTime(jour, heure).toZonedDateTime(fuseau, {disambiguation: 'compatible'})` : heure inexistante → décalée de la durée du saut (02:30 → 03:30 le jour du passage à l'heure d'été), heure ambiguë → la première occurrence.
- Planification : deux tâches périodiques à chaque passage cron (chaque minute), `schedule-occurrence-reminders` et `schedule-daily-reminders`. Un rappel est mis en file (tâche `notify` immédiate, sans `run_at` futur) quand son instant est atteint et date de **moins d'une heure** ; au-delà (cron interrompu), il est abandonné plutôt qu'envoyé à contretemps. Planifier « au moment voulu » (et non à l'avance) fait qu'un changement de réglage s'applique sans tâche orpheline à annuler.
- Clés d'unicité : `occurrence-reminder:<échéance>:J-3|J` et `daily-reminder:<compte>:<jour local>` ; changer d'heure dans la journée ne produit pas de second rappel le même jour.
- Rappels d'échéance : échéances `pending` seulement (une échéance payée ou sautée n'en reçoit plus), récurrence et carnet non supprimés, destinataire = propriétaire du carnet (fuseau et heure de rappel du propriétaire, comme ADR-033). Pré-filtre SQL `due_date ∈ [J_utc − 2, J_utc + 4]` (index `occurrence_reminder_idx (status, due_date)`), pagination par `(due_date, id)`. En mode auto, l'échéance est payée à minuit locale (ADR-033) : le rappel « jour J » ne part donc qu'en mode confirmation (en plus de la notification `occurrence_due`, à fusionner éventuellement par P4-04).
- Rappel quotidien : envoyé chaque jour même si des dépenses ont déjà été saisies (option la plus simple ; affinable plus tard). Charge utile `{kind:'daily_reminder', userId, date}` ; rappels d'échéance `{kind:'occurrence_reminder', notebookId, occurrenceId, reminder: 'three_days_before'|'due_date'}`. Aucun montant (ADR-003).
- Une ligne en échec (fuseau invalide) n'arrête pas le passage : `ScheduledTaskError` en fin de tâche (identifiants seuls), comme ADR-033.
Conséquences : P4-04 applique plage de silence et réglages par type à l'envoi, ignore une échéance payée/sautée entre la mise en file et l'envoi ; le parcours de tous les comptes à rappel quotidien chaque minute (lots de 500) est acceptable au MVP, à indexer/filtrer par heure si le volume l'exige.

## ADR-035 — Notifications push : appareils, réglages, plage de silence, fusion (2026-11-05)

Contexte : P4-04 (F-NOT-01, F-NOT-04, F-NOT-05). Le cahier demande réglages par type et plage de silence sans préciser défauts, report ni comportement en cas de doublon ; ADR-034 laisse ouverte la fusion `occurrence_due` / rappel « jour J ».
Décision :
- Appareils (migration 0012, table `device`, non synchronisée) : `PUT /me/devices/:id` (UUID v7 tiré par l'application, idempotent) et `DELETE /me/devices/:id`. Jeton unique via `push_token_hash` (SHA-256) : un jeton réenregistré par un autre compte est retiré de l’ancienne ligne et rattaché au nouveau compte (un appareil = un compte connecté) ; un identifiant d’appareil appartenant à un autre compte → 409. Jeton jamais journalisé.
- Réglages (`notification_setting`, une ligne par compte, absente = défauts) : `GET`/`PATCH /me/notification-settings`, quatre interrupteurs (limite, échéance, dépense inhabituelle, rappel quotidien) **activés par défaut**, plage de silence `quiet_start`/`quiet_end` en `HH:MM` locales (NULL = aucune ; début inclus, fin exclue, à cheval sur minuit admis). `occurrence_due` et `occurrence_reminder` relèvent du même type « échéance ».
- Contrôles **à l'envoi** (gestionnaire `notify`), dans l'ordre : destinataire (propriétaire du carnet, partage hors MVP), notification devenue sans objet (carnet/dépense supprimés, période de limite close, échéance payée ou sautée) → abandon silencieux ; type désactivé → abandon ; plage de silence en cours → **report** à la fin de la plage (nouvelle tâche, clé `deferred:<tâche>`, heure de fin inexistante décalée comme ADR-034).
- Rappel quotidien reporté par la plage de silence au lendemain : abandonné (« dépenses du jour » serait faux) ; seul le jour local `date` de la charge utile est servi.
- Fusion : le rappel « jour J » d'une échéance dont `confirmation_requested_at` est renseigné (déjà signalée « à confirmer » à minuit) n'est pas envoyé : un seul message le jour J.
- Services : interface `PushSender` ; APNs (HTTP/2, jeton JWT ES256) et FCM HTTP v1 (compte de service OAuth2) configurés uniquement par variables d'environnement, chaque service facultatif (absent → `unavailable`, rien envoyé). APNs : une session HTTP/2 réutilisée pour tout le passage cron, fermée en fin de passage (Apple déconseille une connexion par envoi). Jeton refusé (APNs 410/`BadDeviceToken`/`Unregistered`, FCM `UNREGISTERED` ou 400 « registration token » ; un 404 FCM seul = configuration erronée → erreur, pas de suppression) → appareil supprimé s'il porte toujours ce jeton. Erreur transitoire sur un appareil : les autres sont servis puis la tâche échoue pour nouvel essai — un doublon sur les appareils déjà servis est accepté (pas de suivi par appareil au MVP).
- Contenu : titres et textes fr/en génériques, données = type et identifiants seulement ; **aucun montant, aucun libellé saisi** (ADR-003).
Conséquences : P4-06 (`DELETE /me`) supprime appareils et réglages (cascade sur `user`) ; l'application mobile (P6-11) enregistre son jeton à chaque démarrage et expose les réglages.

## ADR-036 — Export CSV / Excel des dépenses, fichiers chiffrés à lien expirable (2026-11-05)

Contexte : P4-05 (F-EXP-01, NF-SEC-01, §8.1). Le cahier ne fixe ni colonnes, ni séparateur, ni format des nombres, ni durée du lien (15 min vient du plan) ; le service `Entitlements` n'existe qu'en P5-01.
Décision :
- Parcours : `POST /notebooks/{id}/exports` `{id (UUID v7 client), format csv|xlsx, from, to}` → 202 et tâche `export.generate` (clé `export:<id>`) dans la même transaction ; `GET …/exports/{exportId}` (état `pending|ready|expired|failed`, `expiresAt`) ; `GET …/exports/{exportId}/file` → fichier déchiffré, `Cache-Control: no-store`. Le « lien » est cette route authentifiée (jeton porteur) : pas d'URL signée sans jeton. Seul le demandeur voit son export ; sinon 404. Rejeu du même corps → même export ; identifiant réutilisé autrement → 409.
- Validité : 15 min après génération (`expires_at`) ; au-delà, 404 sur le fichier ; fichier absent ou indéchiffrable (rotation de clé) → 404 aussi. Génération en erreur : retentée par la file, export `failed` au dernier essai ; ligne disparue pendant la génération → fichier effacé. Cas rares restant `pending` jusqu'à la purge à un jour : bail expiré ou délai dépassé au dernier essai (gestionnaire non rappelé). Le 409 d'un identifiant pris ailleurs révèle seulement son existence (UUID v7 tirés par le client : accepté). Tâche périodique `purge-expired-exports` : fichier puis ligne dès l'expiration ; demandes en attente ou en échec depuis plus d'un jour.
- Contenu : dépenses actives du carnet, `spent_on` dans la période (bornes incluses), par date puis id ; colonnes Date, Montant, Devise, Catégorie (racine), Sous-catégorie, Marchand, Note, Étiquettes, Origine, libellés dans la langue du compte (fr par défaut, en sinon). CSV : BOM UTF-8, CRLF, RFC 4180 ; fr = `;` et virgule décimale, en = `,` et point ; montant = chaîne décimale exacte sans groupement ni symbole (`decimalAmount` de `@depenseo/shared`) ; textes commençant par `= + - @` ou tabulation préfixés d'une apostrophe (injection de formule). Excel : SpreadsheetML minimal écrit à la main, zippé par `fflate` 0.8.3 (épinglé) ; dates en numéros de série au format `yyyy-mm-dd`, montants numériques au format selon les décimales de la devise, textes en chaînes en ligne (aucune formule).
- Premium : Excel autorisé si `user.plan ∈ {premium, trial}` (`src/subscriptions/entitlements.ts`), sinon 403 ; **P5-01 remplace cette règle** par `Entitlements` (fait, ADR-040).
- Stockage : `FILE_STORAGE_DIR` (chemin absolu, hors du dossier public) et `FILE_ENCRYPTION_KEY` (32 octets en base64), toutes deux ou aucune ; absentes → `POST` 503 et pas de purge. Fichier `<id>.enc` (0600, dossier 0700, écriture atomique) = « DPF1 » ‖ IV 96 bits aléatoire ‖ tag ‖ AES-256-GCM, identifiant en données associées (fichier échangé ou renommé illisible).
- Rotation de clé : remplacer `FILE_ENCRYPTION_KEY` ; les exports en cours (≤ 15 min) deviennent illisibles → 404, l'utilisateur relance. P4-07/P4-08 (fichiers plus durables) ajouteront un identifiant de clé si besoin.
Conséquences : P4-06 (`DELETE /me`) doit effacer les fichiers `export_file` de l'utilisateur avant la cascade des lignes ; P4-07 réutilise `EncryptedFileStore` ; P6-12 interroge l'état puis télécharge avec le jeton.

## ADR-037 — Suppression du compte `DELETE /me` (2026-11-05)

Contexte : F-AUTH-07 (suppression du compte et de toutes les données depuis l'app), §5 RGPD (effacement), ADR-024 (`purgeNotebook`), ADR-035/036 (appareils, fichiers d'export). Le cahier ne prévoit ni délai, ni confirmation par mot de passe, ni e-mail.
Décision :
- `DELETE /me` → 204, **immédiat et définitif**, sans période de grâce ni ressaisie du mot de passe (interprétation la plus simple ; la confirmation est un écran de l'app, P6-12). Compte déjà supprimé (jeton d'accès encore signé ≤ 15 min) → 401.
- Une transaction (`deleteAccount`, `src/me/account-deletion.ts`) : verrou du compte puis des carnets possédés (ordre d'id) ; suppression des tâches `job` dont la charge utile ou la clé d'unicité cite le compte, un carnet possédé ou un export (toute notification de carnet porte `notebookId`, un report `deferred:` recopie la charge utile) ; `purgeNotebook` par carnet (qui purge désormais aussi `spending_limit`, FK catégorie sans cascade) ; suppression de `user`, la cascade emporte sessions, jetons, identités, appareils, réglages, adhésions, exports ; fichiers chiffrés effacés **avant** la validation (un échec de validation laisse des lignes sans fichier, jamais un fichier sans ligne).
- Journal d'audit : conservé mais **pseudonymisé** (`actor_user_id` = NULL s'il désigne le compte, `target_id` = NULL s'il désigne le compte, un carnet possédé ou un export) : la trace des accès admin survit sans désigner la personne.
- Partage hors MVP : un carnet possédé est purgé **en entier**, y compris ce qu'y auraient saisi d'autres membres ; F-PAR devra choisir entre transfert de propriété et refus 409 (`TODO(F-PAR)` dans le code). Membre du carnet d'autrui : seule l'adhésion disparaît (les dépenses n'ont pas de colonne auteur).
- Tâches : lecture sans verrou des `job` qui citent un identifiant, puis suppression par clé.
- Test : `test/support/user-references.ts` parcourt `information_schema` (colonnes BINARY(16) et texte), calcule la fermeture des identifiants rattachés au compte, et exige (1) que la fixture touche **toutes** les tables — une nouvelle table casse le test tant qu'elle n'y est pas ajoutée — puis (2) qu'aucune ligne ne référence plus le compte ni son e-mail après suppression, autrui intact.
Limites :
- Sauvegardes (P4-08) : les données effacées subsistent dans les exports horaires chiffrés jusqu'à leur rotation ; la durée de conservation doit figurer dans la politique de confidentialité (rappel noté dans P4-08).
- Courses : `ExportsService.request` et `registerDevice` prennent les verrous dans l'ordre inverse (carnet ou appareil puis `user` par la FK) : 1213 attendu, rejoué par `withTransaction`, puis 1452 → 500 côté écrivain perdant (rare, acceptable). Un cron (rappels, report `deferred:`) peut encore créer une tâche citant le compte après la suppression : ses gestionnaires abandonnent une cible absente et la ligne est purgée à 7 jours.
- Stockage de fichiers désactivé (variables retirées) : d'éventuels anciens `<id>.enc` restent sur le disque ; les retirer à la main lors d'un tel changement.
- La révocation des jetons Sign in with Apple (exigence App Store) n'est pas faite, l'API ne conservant aucun jeton de rafraîchissement Apple (à traiter avec P6 si l'App Review l'exige) ; abonnements en cours non résiliés côté store (l'utilisateur résilie dans le store, §5) — P5-01 devra purger ses tables ici et la fixture le rappellera.

## ADR-038 — Export RGPD des données du compte `POST /me/export` (2026-11-05)

Contexte : F-AUTH-08 (export complet JSON et CSV), §5 RGPD (droits d'accès et de portabilité), plan P4-07 (« zip chiffré, tâche de fond, lien expirable »). Le cahier ne fixe ni structure, ni durée du lien, ni sens de « zip chiffré ».
Décision :
- Parcours calqué sur ADR-036 : `POST /me/export` `{id (UUID v7 client)}` → 202 et tâche `account_export.generate` (clé `account-export:<id>`) dans la même transaction, sous verrou de la ligne `user` (même ordre que `DELETE /me`) ; `GET /me/export/{exportId}` (état `pending|ready|expired|failed`) ; `GET /me/export/{exportId}/file` → `application/zip`, `Cache-Control: no-store`. Seul le compte demandeur voit sa demande (404 sinon) ; rejeu → même demande ; identifiant d'autrui → 409. Table `account_export` (migration 0014, cascade sur `user`), purgée par `purge-expired-exports` comme `export_file`.
- « Zip chiffré » = archive chiffrée **au repos** par `EncryptedFileStore` (AES-256-GCM, NF-SEC-01) et servie par TLS à la seule session du compte, lien valable 15 min. Pas de zip protégé par mot de passe : ZipCrypto est cassé, AES-zip n'est pas géré par `fflate` et imposerait un mot de passe à transmettre (interprétation la plus simple).
- Contenu : `depenseo.json` (`{format, version: 1, generatedAt, tables: {<table SQL>: lignes}}`), `csv/<table>.csv` (RFC 4180, `,`, BOM, protection contre l'injection de formule) et `LISEZMOI.txt`. Format technique lisible par machine (portabilité) : propriétés de schéma, montants en unités mineures, dates calendaires telles quelles, horodatages ISO UTC. Périmètre (`src/account-export/personal-data.ts`) : compte, identités, réglages, appareils, sessions, jetons e-mail, carnets possédés ou rejoints et tout leur contenu (lignes supprimées logiquement comprises : encore détenues), ses propres adhésions, ses exports, lignes du journal d'audit dont la **cible** est le compte, un de ses carnets ou exports (sans l'identité de l'administrateur) ; les actions d'un compte administrateur sur autrui sont exclues (données de tiers). Exclus : table `job` (technique, identifiants seuls, 7 jours) ; propriétés `passwordHash`, `adminTotpSecret`, `tokenHash`, `pushToken`, `pushTokenHash`, `subjectHash`, `actorUserId` (secrets ou accréditations). Toute valeur binaire non prévue fait échouer la génération (décision explicite exigée).
- Test : avec la fixture commune `test/support/populated-account.ts` (une ligne dans chaque table, partagée avec la suppression), l'ensemble des tables de l'archive doit égaler l'ensemble des tables qui référencent le compte (information_schema, `ownedIds`/`referencingRows`) moins les exclusions déclarées : une table future casse le test de suppression puis celui-ci tant qu'elle n'est pas couverte.
Limites : aucune limite de fréquence des demandes (génération en tâche de fond, coût borné par le volume d'un compte) ; carnet partagé (hors MVP) : un membre exporterait tout le carnet, ce que F-PAR devra revoir ; génération en mémoire (volume MVP modeste) ; lectures successives hors transaction (READ COMMITTED) : une écriture concurrente peut rendre l'archive légèrement incohérente (ex. liaison d'étiquette sans sa dépense), l'utilisateur peut relancer.

## ADR-039 — Export horaire chiffré de la base et restauration (2026-11-05)

Contexte : NF-DISP-01 (perte maximale 1 h « reposant sur un export horaire », reprise < 4 h), NF-SEC-01 (exports de sauvegarde chiffrés par l'application, clés hors code, rotation), §8.2 (JetBackup quotidien, export horaire par cron, copie quotidienne chez un second prestataire UE, restauration testée), plan P4-08. Le cahier ne fixe ni outil, ni format, ni rétention de l'export horaire.
Décision :
- Export logique écrit en Node (`src/backup/db-dump.ts`), sans `mysqldump` (présence non garantie chez o2switch, et absent de la CI) : `SHOW CREATE TABLE` puis `INSERT` multi-lignes (≈ 512 Kio par instruction), une instruction par ligne (chaînes échappées par mysql2), en-tête `-- depenseo-dump v1 <instant>` et marque de fin vérifiées avant toute écriture à la restauration (export tronqué refusé). Fichier lisible aussi par le client `mariadb` en dernier recours.

Valeurs lues et réécrites en chaînes (`dateStrings: true`, `bigNumberStrings`, DECIMAL en chaîne, session `+00:00`) : aucune conversion par `Date` ni flottant. Colonnes générées exclues des `INSERT` (recalculées). Collation par défaut de la base rétablie (`ALTER DATABASE`). `sql_mode` strict fixé par l'en-tête ; clés étrangères désactivées pendant le chargement. Vues, déclencheurs, routines et événements non gérés : un test échoue si le schéma en introduit.
- Fichier `BACKUP_DIR/depenseo-AAAAMMJJTHHMMSSZ.sql.gz.enc` : gzip puis AES-256-GCM au format « DPF1 » d'ADR-036 (données associées constantes `depenseo-db-export-v1` : le fichier peut être renommé ou copié ailleurs), écrit atomiquement (renommage), mode 0600. Clé **dédiée** `BACKUP_ENCRYPTION_KEY`, distincte de `FILE_ENCRYPTION_KEY` : elle doit être conservée **hors du serveur** (sinon la perte du serveur rend les sauvegardes inutiles) et sa rotation ne doit pas dépendre de celle des fichiers servis.

Compte de lecture = compte API (`DATABASE_URL`) ; restauration = `RESTORE_DATABASE_URL` (compte migrator) vers une base **vide** (refus sinon). Scripts `apps/api/scripts/db-export.ts` / `db-restore.ts` (`pnpm --filter api db:export|db:restore`) — le plan citait `scripts/db-export.ts` : les scripts TypeScript vivent dans `apps/api/scripts` (compilés avec l'API).
- Procédure, cron, rétention et copie hors site : `docs/dev/BACKUP.md`.
Limites : seuls chaînes, entiers sûrs, binaires et NULL sont recopiés (`sqlLiteral`) ; tout autre type (JSON lu en objet sous MySQL 8, BIT…) fait échouer l'export plutôt que de le corrompre ; un fichier au nom daté dans le futur (horloge décalée) n'est pas supprimé par la rotation ; export et chiffrement en mémoire (fichier compressé entier ; volume MVP de quelques Mio) — passer à un chiffrement en flux si l'export compressé dépasse ~100 Mio ; la copie quotidienne chez un second prestataire et la conservation JetBackup relèvent de l'exploitation (actions humaines, BACKUP.md) ; base de test `depenseo_restore_test` créée par `docker/mariadb/initdb.d` (volume existant : la créer à la main, cf. BACKUP.md).

## ADR-040 — Abonnements : vérification des achats, essai de 14 jours, droits Premium (2026-11-05)

Contexte : F-ABO-01 (achats vérifiés côté serveur), F-ABO-02 (essai de 14 jours), F-ABO-03 (restauration, multi-appareils liés au compte), §5 (Premium 2,49 €/mois ou 19,99 €/an, essai « sans engagement »), ADR-001 (vérification directe derrière `StoreReceiptVerifier`), plan P5-01. Le cahier ne fixe ni le protocole, ni le déclenchement de l'essai, ni le sort d'un achat présenté par un autre compte.
Décision :
- Interface `StoreReceiptVerifier` (`src/subscriptions/store-receipt-verifier.ts`) : preuve `{store: 'app_store', transactionId}` (StoreKit 2) ou `{store: 'google_play', purchaseToken}` → `VerifiedPurchase {purchaseKey, productCode, status, expiresAt}` ; `InvalidReceiptError` → 400, `StoreUnavailableError` → 503. Faux vérificateur en test (`startTestApp({ storeVerifier })`).
- App Store : App Store Server API « Get All Subscription Statuses » (`GET /inApps/v1/subscriptions/{transactionId}`, jeton ES256 de la clé In-App Purchase, `aud: appstoreconnect-v1`, `bid`) ; bundle contrôlé ; clé d'achat = `originalTransactionId` ; statuts Apple 1/4 → `active` (grâce : droits jusqu'à `gracePeriodExpiresDate`), 3 → `suspended`, 2 → `expired`, 5 ou `revocationDate` → `revoked`. Environnement unique par configuration (`APP_STORE_ENVIRONMENT`, production par défaut ; pas de repli automatique vers le bac à sable). Les JWS de la réponse (TLS direct depuis Apple) sont **décodés sans vérifier leur chaîne x5c** : la vérification jusqu'à l'Apple Root CA G3 arrive en P5-02 (notifications, où elle est indispensable) et sera appliquée ici aussi (TODO).
- Google Play : `purchases.subscriptionsv2.get` (jeton OAuth du compte de service, portée `androidpublisher`, code commun avec FCM : `src/google/service-account-token.ts`) ; clé d'achat = jeton d'achat ; `ACTIVE`, `IN_GRACE_PERIOD`, `CANCELED` → `active` jusqu'à `expiryTime` ; `ON_HOLD`, `PAUSED`, `PENDING` → `suspended` ; `EXPIRED` → `expired`. L'accusé de réception (3 jours) est fait par l'application (Play Billing Library), pas par l'API. `linkedPurchaseToken` (montée de gamme) non suivi : l'ancienne ligne expire d'elle-même.
- Produits Premium : `premium_monthly`, `premium_yearly`, mêmes identifiants dans les deux stores (constante `PREMIUM_PRODUCTS`) ; tout autre produit → 400. **Aucune offre d'introduction (essai gratuit store) ne doit être configurée** : l'essai est celui de l'API. Plusieurs achats dans une réponse : un `active` passe avant tout autre, puis l'échéance la plus tardive. Réponse 200 illisible, clé d'API inutilisable → 503 (jamais « reçu invalide » à tort).
- Table `subscription` (migration 0015) : une ligne par achat, unique `(store, purchase_key_hash)` (SHA-256 de la clé d'achat, jamais en clair, exclue de l'export RGPD), cascade sur `user`. Rattachement : l'application **doit** transmettre l'identifiant du compte au store à l'achat (`appAccountToken` StoreKit 2, `obfuscatedExternalAccountId` Play Billing — P6-13) ; s'il figure dans la réponse du store et désigne un autre compte → 409. À défaut, l'achat appartient au **premier compte** qui le présente. Restauration par le même compte (autre appareil) = mise à jour de la ligne ; présenté par un autre compte → 409 (pas de transfert : interprétation la plus simple de « lié au compte », évite le partage d'un abonnement entre comptes et la prise d'un achat par qui devinerait un `transactionId`). Un compte supprimé libère l'achat (cascade).
- Essai : `POST /subscriptions/trial`, déclenché explicitement par l'utilisateur, **sans passage par le store** (« sans engagement » : aucun moyen de paiement), une fois par compte (`user.trial_ends_at` non NULL = consommé → 409, même expiré), sous verrou de la ligne `user`. Le jour du début est le jour 1 ; fin = minuit local (fuseau du compte au début, désambiguïsation `compatible`) au début du jour 15. Un compte supprimé puis recréé avec la même adresse peut refaire un essai (aucune trace conservée, RGPD).
- Droits (`src/subscriptions/entitlements.ts`, « service Entitlements ») : `premium` si un abonnement `active` non échu (fin = la plus tardive), sinon `trial` si l'essai court, sinon `free` ; `GET /subscriptions` les expose ; l'export Excel (ADR-009/036) les consulte. La colonne provisoire `user.plan` est supprimée (migration 0016, aucune donnée de production).
- Configuration : groupes tout-ou-rien `APP_STORE_*` et `GOOGLE_PLAY_*` dans `env.ts` ; absent → vérification 503 pour ce store, démarrage accepté.
Limites : pas de limite de débit sur `POST /subscriptions/verify` (un compte pourrait consommer le quota des API des stores ; à ajouter si constaté, cf. `mail-throttle`) ; l'essai reste accordé à un compte déjà Premium (consommé sans effet visible) ; statut rafraîchi seulement à la vérification (renouvellements, remboursements et expirations suivis par les notifications serveur en P5-02) ; la lecture seule des fonctions Premium à expiration (§5) relève de P5-02.

## ADR-041 — Notifications serveur des stores, signatures Apple, lecture seule à expiration (2026-11-05)

Contexte : F-ABO-01 (« notifications serveur des stores »), §5 (« à la fin du Premium, aucune donnée n'est supprimée : les fonctions Premium passent en lecture seule »), ADR-040 (TODO : chaîne x5c non vérifiée), plan P5-02. Le cahier ne fixe ni le format ni le traitement des notifications.
Décision :
- Routes publiques (garde d'accès) `POST /api/v1/store-notifications/app-store` et `…/google-play`, ajoutées à la liste blanche et au contrat OpenAPI (le test de liste blanche énumère les routes par OpenAPI : exclure le contrôleur l'aurait rendu aveugle). 200 = reçue ; 401 = authentification refusée ; 400 = corps invalide ; 503 = store non configuré ou injoignable (le store relivre).
- **La notification n'est qu'un signal** : une fois authentifiée, l'achat désigné est relu auprès du store par le `StoreReceiptVerifier` (App Store : `originalTransactionId` de la transaction signée ; Google : `purchaseToken` de `subscriptionNotification`, ou de `voidedPurchaseNotification` si `productType = 1`), puis `SubscriptionsService.refresh` met à jour la ligne `subscription` existante (statut, échéance, produit). Insensible à l'ordre d'arrivée et au rejeu (aucune table d'événements ni contrôle de `signedDate`/`messageId`), réutilise la normalisation d'ADR-040. Achat inconnu du store ou jamais présenté par un compte : ignoré (200) — l'application le présentera par `POST /subscriptions/verify` ; pas de création de ligne depuis une notification. Autre bundle/paquet, autre environnement Apple (`APP_STORE_ENVIRONMENT`), notification sans transaction (TEST…) : ignorés (200).
- App Store : `AppleSignedDataVerifier` (`src/subscriptions/apple-signed-data.ts`) — JWS ES256, `x5c` de 3 certificats, racine = Apple Root CA - G3 embarquée (empreinte SHA-256 vérifiée par test), chaque certificat émis et signé par le suivant, validité à l'horloge applicative, intermédiaire CA avec OID 1.2.840.113635.100.6.2.1, feuille non CA avec OID 1.2.840.113635.100.6.11.1, puis signature du JWS par la clé de la feuille. Appliqué aussi aux JWS de l'App Store Server API (clôt le TODO d'ADR-040 ; JWS refusé → 503, jamais « reçu invalide »). Pas de contrôle de révocation en ligne (OCSP) : la racine et la relecture par l'API suffisent. PKI de test : `apps/api/test/fixtures/apple-pki/` (script `generate.sh`, clés de test seulement), injectée par `startTestApp({ storeNotificationKeys })`.
- Google Play : push Pub/Sub authentifié — `Authorization: Bearer <jeton OIDC Google>` RS256 vérifié contre le JWKS Google (`iss` accounts.google.com, `aud` = `GOOGLE_PLAY_PUSH_AUDIENCE`, `email` = `GOOGLE_PLAY_PUSH_SERVICE_ACCOUNT` avec `email_verified`). Variables groupées tout-ou-rien ; absentes → 503. JWKS injoignable → 503.
- Lecture seule à expiration (§5) : les droits se calculent à la lecture (`expires_at` et statut, ADR-040), donc un abonnement expire même sans notification ; la notification ne fait que rafraîchir plus tôt (révocation, remboursement). Hors Premium, la création d'un export Excel est refusée (403) ; rien n'est supprimé (ligne `subscription` conservée avec son statut, dépenses et exports déjà produits intacts, CSV toujours permis). Les autres fonctions Premium (limites par catégorie, pièces jointes, devises…) sont hors MVP : elles devront appliquer la même règle (lecture permise, création/modification refusée par `Entitlements`).
Limites : un achat relu sous un produit non Premium (changement d'offre hors catalogue) est ignoré par `refresh` : la ligne garde ses droits jusqu'à son `expires_at` ; recherche des OID dans le DER entier (Node n'expose pas les extensions), sans incidence une fois la chaîne ancrée sur la racine Apple ; deux instances du vérificateur Apple (notifications, App Store Server API) construites avec les mêmes racines ; clés privées de test `*.key` committées sous `test/fixtures/apple-pki` (à exclure d'un éventuel scanner de secrets) ; pas de limite de débit sur les deux routes (chaque notification valide déclenche un appel au store ; une notification Apple valide rejouée en boucle consommerait le quota de l'API) ; à configurer par l'humain : URL de notification v2 dans App Store Connect, sujet RTDN + abonnement push authentifié (compte de service, audience) dans la console Google Cloud.

## ADR-042 — Back-office : rôle par script, TOTP, cookie `Path=/admin`, 404 et audit (2026-11-05)

Contexte : F-ADM-01 (rôle admin + double authentification), F-ADM-03 (404 sur `/admin` et les routes admin de l'API, rôle attribué par script), §8.5 (cookie `HttpOnly; Secure; SameSite=Strict`, chemin `/admin`), §8.3 (secret TOTP chiffré), NF-SEC-06 (audit des accès admin), plan P5-03. Le cahier ne fixe ni durée de session, ni plafond d'essais, ni format d'audit, ni l'emplacement des routes admin.
Décision :
- **API admin sous `/admin/api/*`**, hors du préfixe `/api/v1` (`setGlobalPrefix(…, { exclude: ['admin{/*rest}'] })`) : un cookie `Path=/admin` n'est pas envoyé à `/api/v1/admin/*`. Aucune route n'existe sous `/api/v1/admin` (404 de route inexistante, testé). Contrôleurs admin = décorateur `AdminController(path)` : préfixe, métadonnée `ADMIN_AREA` (la garde Bearer globale s'efface), `AdminGuard`, `@ApiExcludeController` (absents de l'OpenAPI public et donc du client généré, F-ADM-02). La SPA du back-office (P5-05) sera servie sous `/admin`.
- **404 partout** : sans cookie, cookie invalide/expiré/forgé, compte sans rôle `admin` ou sans secret TOTP, back-office non configuré → `NotFoundException`, réponse identique (statut, type, corps hors `instance`) à une route inexistante, sans `WWW-Authenticate`. La connexion `POST /admin/api/session` répond aussi 404 à **tout** échec (corps invalide, mauvais mot de passe, compte non admin, code faux, rejeu, blocage) : un non-admin n'apprend rien. Succès : 204 + cookie.
- **TOTP** RFC 6238 (SHA-1, 6 chiffres, 30 s, ±1 pas) codé sur `node:crypto` (`src/admin/totp.ts`, vecteurs de la RFC en test), sans dépendance. Secret de 160 bits chiffré AES-256-GCM (`ADMIN_TOTP_KEY`, données associées = id du compte) dans `user.admin_totp_secret`. **Rejeu** : `user.admin_totp_last_step` (migration 0017) ; un pas ≤ dernier pas consommé est refusé. **Plafond** : 5 codes refusés en 15 min (comptés dans `audit_log`) bloquent la connexion du compte jusqu'à ce que la fenêtre glisse ; tentatives sérialisées par `SELECT … FOR UPDATE` sur le compte. Pas de codes de secours : en cas de perte, réattribution par le script (nouveau secret).
- **Session** : JWT HS256 sans état, clé `ADMIN_SESSION_SECRET` et audience `depenseo-admin` propres (un jeton mobile n'ouvre pas le back-office, le cookie n'est pas un Bearer valide), durée **absolue de 30 min**, cookie `depenseo_admin` `HttpOnly; Secure; SameSite=Strict; Path=/admin; Max-Age=1800`. Le jeton porte l'empreinte (`enr`) du secret TOTP chiffré en vigueur ; rôle, secret et empreinte sont relus en base à **chaque** requête : retrait du rôle ou réattribution (nouveau secret) = sessions ouvertes caduques immédiatement. `ADMIN_SESSION_SECRET` identique à `JWT_ACCESS_SECRET` = démarrage refusé. Déconnexion = effacement du cookie (le jeton reste valable ≤ 30 min s'il a été copié : risque accepté, pas de table de sessions). CSRF : `SameSite=Strict` et même domaine (§8.4).
- **Attribution** : `scripts/grant-admin.ts` (`pnpm --filter api admin:grant <email>` / `--revoke <email>`, variables `DATABASE_URL`, `ADMIN_TOTP_KEY`), seul chemin d'écriture de `user.role`. Compte vérifié et doté d'un mot de passe requis. Chaque attribution tire un nouveau secret et affiche une fois l'URI `otpauth://`, **seulement si la sortie est un terminal** (sinon refus : le secret finirait dans un fichier ou un journal) ; le retrait efface rôle, secret et dernier pas.
- **Audit** (`audit_log`, nouvelle colonne `route`) : `admin.grant`/`admin.revoke` (acteur NULL = script, cible = compte), `admin.login`, `admin.login_failed` (seulement quand le mot de passe d'un admin est correct), `admin.login_blocked`, et `admin.access` pour **chaque** requête admin authentifiée, écrite avant la route (échec d'écriture = refus) avec le motif Express (`GET /admin/api/session`), jamais l'URL réelle ni la requête. Aucun montant ni e-mail. Les accès d'un admin aux données d'un compte (P5-04) renseigneront `target_type`/`target_id`.
- Variables `ADMIN_SESSION_SECRET` (≥ 32 caractères) et `ADMIN_TOTP_KEY` (AES-256 base64) groupées tout-ou-rien ; absentes = back-office désactivé (404 partout).
Limites : jeton non révocable avant expiration hors retrait du rôle ; plafond d'échecs par compte seulement (pas par IP ; la force brute du mot de passe relève de la connexion ordinaire) ; un admin bloqué l'est aussi pour 15 min quand un tiers connaît son mot de passe (il doit alors le changer) ; l'audit grossit sans purge (volume faible, à revoir en P5-04) ; plafond d'échecs sérialisé par verrou mais non éprouvé par un test de concurrence ; le back-office et le script utilisent le compte de base de l'API (`DATABASE_URL`), le compte distinct de §8.3 (`depenseo_admin`) reste à brancher (P5-04/P5-05) ; `/admin` est aujourd'hui 404 pour tous (aucune page servie) — P5-05 rendra publique la seule page de connexion (§8.5) et devra adapter `admin-access.spec.ts`.

## ADR-043 — Routes du back-office : comptes, abonnements, tâches, statistiques, audit (2026-11-05)

Contexte : F-ADM-01 cite « utilisateurs, abonnements, journaux, statistiques » sans fixer les champs ; NF-SEC-06 et la minimisation RGPD interdisent montants et données superflues. Le cahier des charges ne prévoit aucune action d'administration sur un compte (suspension, suppression).
Décision (interprétation la plus simple) :
- **Lecture seule**, sauf la relance d'une tâche en échec. Routes `@AdminController` (404 sans session, `admin.access` avec le motif de route) : `GET /admin/api/users?q&limit&cursor`, `GET /admin/api/users/{userId}`, `GET /admin/api/subscriptions?userId&store&status`, `GET /admin/api/jobs?status` (défaut `failed`), `POST /admin/api/jobs/{jobId}/retry`, `GET /admin/api/stats`, `GET /admin/api/audit?actorUserId&targetId&action`. Toutes `Cache-Control: no-store`.
- **Comptes** : liste = id, e-mail, vérifié, rôle, date de création ; recherche par fragment d'e-mail (LIKE échappé `!`). Fiche = + langue, fuseau, devise, mot de passe présent (booléen), fournisseurs Apple/Google, nombre d'appareils par plateforme, de carnets et de dépenses non supprimées, droits (`loadEntitlements`), abonnements. Jamais de montant, note, marchand, catégorie, jeton, empreinte ni secret. La consultation d'une fiche ajoute `admin.user_view` (cible `user`).
- **Tâches** : liste sans charge utile (identifiants seulement, mais inutile à l'exploitation). Relance = `failed` → `pending`, `attempts` 0, `run_at` = maintenant, erreur/bail/fin effacés, sous `FOR UPDATE` ; autre statut → 409 ; tracée `admin.job_retry` (cible `job`). Le gestionnaire étant idempotent (ADR-016), la relance est sans risque.
- **Statistiques** : compteurs seulement — comptes (total, vérifiés, admins), inscriptions par jour UTC sur 30 jours, comptes Premium (abonnement actif non expiré) et en essai sans abonnement, abonnements par statut et actifs par store, dépenses (total, créées sur 30 jours), tâches par statut. Aucune somme.
- Pagination par curseur opaque `(created_at, id)` décroissant, 50 par défaut, 100 au plus.
- **Audit** : index `audit_log(target_id, created_at)` (migration 0018) pour le filtre par cible. **Pas de purge** : le journal d'audit est la preuve des accès administrateurs (NF-SEC-06), volume faible (un administrateur, quelques requêtes par jour) ; une durée de conservation sera fixée avec la politique de rétention (P7). La consultation d'une fiche inexistante n'écrit que `admin.access` (motif de route, sans l'identifiant).
- **Compte de base `depenseo_admin` (§8.3)** : non branché, l'API admin partage le pool de l'API (même processus Passenger). Reporté à P5-05 (service du build admin) ; à défaut, à consigner comme écart dans un ADR de P5-05.
- Statistiques « 30 jours » = 30 jours calendaires UTC (aujourd'hui compris) pour `signups` comme pour `expenses.createdLast30Days`.
Limites : pas d'export des listes, pas de recherche plein texte ; les compteurs sont calculés à la demande (requêtes d'agrégat sur tables entières) ; tri des comptes par `created_at` et des tâches par `created_at` sans index dédié (tri complet, acceptable au volume MVP).

## ADR-044 — Application `apps/admin` : page de connexion publique, application servie à une session admin (2026-11-05)

Contexte : §8.1 (React-admin, Vite, Playwright) et §8.5 : « seule la page de connexion, sans code d'administration, est publique ; l'API ne sert les fichiers de l'application d'administration qu'à une session administrateur ». F-ADM-02 : aucun code admin dans l'app mobile ni dans les bundles publics. ADR-042 laissait `/admin` à 404 pour tous en attendant P5-05.

- **Service par l'API** (`AdminConsoleController`, `src/admin/admin-console*.ts`) : `GET /admin/login` et `/admin/login/assets/:file` publics (`@AdminLogin`) ; `GET /admin` (`/admin/`) et `/admin/assets/:file` derrière `AdminGuard` (404 identique à une route inexistante, ligne `admin.access` par fichier servi). Aucune autre URL. Fichiers chargés **en mémoire au démarrage** depuis `ADMIN_DIST_DIR` (chemin absolu, facultatif : absent = pages 404, API admin intacte ; dossier incomplet = démarrage refusé) : seul un nom présent dans le build est servable, aucun chemin de requête n'atteint le disque (pas de traversée possible) ; les deux zones ne partagent aucun fichier. En-têtes : `Cache-Control: no-store`, `nosniff`, `Referrer-Policy: no-referrer`, CSP `default-src 'self'` + `frame-ancestors 'none'` (`style-src 'unsafe-inline'` exigé par MUI/emotion).
- `AccessTokenGuard` laisse aussi passer `/admin` exact (sans barre finale) vers `AdminGuard`, sinon un 401 Bearer trahissait la route.
- Client : `authProvider` vérifie `GET /admin/api/session` ; un 404 d'API n'est traité comme une déconnexion que si la session ne répond plus (une fiche absente ne déconnecte pas) ; redirection par URL absolue vers `/admin/login`. `dataProvider` en **lecture seule** (seule écriture : relance d'une tâche), pagination par curseur traduite en pagination partielle (`pageInfo`) : curseurs mémorisés par liste (ressource + filtres + taille) ; page > 1 sans curseur connu (lien direct) = erreur « revenir à la première page ». Pas d'export CSV des listes. Interface en français (`ra-language-french`), horodatages au format fr-FR dans le fuseau du navigateur, dates calendaires affichées telles quelles.
- **F-ADM-02** : `scripts/check-no-admin-code.mjs` (`pnpm check:admin-code`, en CI après le build) cherche des marqueurs (React-admin/ra-*, `/admin/api/` autre que `session`, actions d'audit admin) dans `mobile/`, `apps/admin/dist/login`, `apps/web/dist`, `packages/api-client`, `apps/api/openapi.json` ; `mobile/` ne doit mentionner ni `/admin` ni `depenseo_admin`. Contre-épreuve intégrée : les marqueurs doivent reconnaître `dist/app`, sinon échec (marqueurs périmés).
- **E2E Playwright** (`apps/admin/e2e`, `pnpm --filter @depenseo/admin test:e2e`) : serveur `apps/api/test/e2e/admin-e2e-server.ts` compilé par `tsc` (`build:e2e` → `dist-e2e/`, décorateurs Nest), base `depenseo_test` migrée, un admin et un compte ordinaire créés au démarrage, identifiants dans un fichier temporaire. Chromium seul, un worker (code TOTP à usage unique). Jamais en parallèle de Vitest (même base).
- **Écart §8.3 — compte de base `depenseo_admin`** : non branché. L'API admin tourne dans le même processus Passenger que l'API publique ; un second pool sous un autre compte n'apporterait d'isolation qu'au prix d'une seconde configuration de pool et de droits SQL à maintenir, sans séparation de processus. À reprendre avec la documentation de déploiement (P7-07, « utilisateurs de base séparés ») si l'hébergeur permet une seconde application Passenger dédiée au back-office.
Limites : bundle admin ~1 Mo non découpé ; un accès à chaque fichier statique produit une ligne d'audit (volume faible) ; la CSP du reste de l'API reste à P7-03.

## ADR-046 — Squelette mobile : SQLCipher par les hooks de `sqlite3`, clé et jetons dans le stockage sécurisé (2026-11-05)

Contexte : §8.1 (Flutter 3, Riverpod, Drift + SQLCipher), NF-SEC-02 (jetons dans le trousseau / Keystore), F-ADM-02, §2 (iOS 15+, Android 8+, fr/en).
Décision :

Client `dio` : origine `--dart-define=API_BASE_URL` (défaut `http://localhost:3000` ; build de release : `https` exigé, sinon arrêt), préfixe `/api/v1`, Bearer relu à chaque requête, délais 10 s / 30 s. Rafraîchissement sérialisé (ADR-018) en P6-02.
- **App** : `MaterialApp.router` + go_router (une route `/`), Riverpod 3, ARB fr (modèle) / en, repli fr, Material 3 clair/sombre selon le système ; iOS : `CFBundleLocalizations` fr/en, région de développement fr. Identifiant `fr.depenseo.depenseo` (Android `applicationId`, iOS bundle), modifiable jusqu'à la première publication ; minSdk 26, iOS 15.
- Code généré (Drift `*.g.dart`, `lib/l10n/generated/`) **committé** ; la CI régénère et exige un diff vide, puis `dart format --set-exit-if-changed`.
Limites : sur Linux/Android, la build SQLCipher lie OpenSSL (licence à mentionner dans les mentions légales, P6-12) ; les binaires sont téléchargés depuis les releases GitHub de `sqlite3.dart` (empreintes sha256 vérifiées par le paquet).

## ADR-047 — Auth mobile : refresh sérialisé dans le client HTTP, liens e-mail ouverts par l'app, Apple sur iOS seulement (2026-11-05)

Contexte : P6-02 (F-AUTH-01/02/03, NF-SEC-02). ADR-018 impose de sérialiser les refresh (usage unique, sans délai de grâce) ; les liens e-mail pointent vers `PUBLIC_WEB_URL/verify-email#token=…` et `/reset-password#token=…` alors que le web est V2 ; `google_sign_in` 7 n'accepte qu'un `initialize` (et donc un nonce) par processus.

- **Refresh** : intercepteur Dio (`lib/core/api/api_client.dart`). Sur 401 d'une requête partie avec un jeton : si le coffre porte déjà un autre jeton d'accès, rejeu direct ; sinon **un seul** `POST /auth/refresh` en vol, partagé par toutes les requêtes (`_refreshing ??=` affecté sans `await` préalable). Un seul rejeu par requête. Refresh refusé (400 ou 401) → coffre vidé + `sessionExpired` (une fois, même pour plusieurs requêtes) → retour à la connexion ; panne réseau ou 5xx → session conservée, erreur d'origine remontée. **Limite** : si le serveur a fait tourner le jeton mais que la réponse est perdue, le refresh conservé est déjà consommé ; l'échange suivant est une réutilisation, la famille est révoquée et l'utilisateur doit se reconnecter (conséquence d'ADR-018 sans délai de grâce, acceptée). `TokenStore` sérialise ses opérations et compte des **générations** : une rotation lancée avant une déconnexion ou une nouvelle connexion n'écrit ni n'efface la session qui l'a remplacée. Le refresh est écrit avant le jeton d'accès. Les routes `/auth/*` ne reçoivent jamais de jeton ni de refresh. Pas de refresh préventif (le 401 suffit, `expiresIn` ignoré).
- **Liens e-mail** : l'app sert les chemins `/verify-email` et `/reset-password` (go_router) et lit `token` dans le fragment (repli `?token=`), quel que soit l'état de session. La vérification est appelée dès l'ouverture de l'écran. La configuration de plateforme des liens universels (Associated Domains iOS, `intent-filter autoVerify` Android, fichiers `apple-app-site-association`/`assetlinks.json` servis par `PUBLIC_WEB_URL`) dépend du domaine de production : à faire au déploiement (P7-07). Pas de session ouverte après vérification ni après réinitialisation (ADR-019) : l'utilisateur se connecte.
- **Apple/Google** : interface `SocialSignIn` ; `PlatformSocialSignIn` reçoit les appels SDK en paramètres (contrat du nonce testé sans SDK) (SDK `sign_in_with_apple` 8.2, `google_sign_in` 7.2). Nonce brut 32 octets base64url, empreinte SHA-256 hex au fournisseur (ADR-020). Google : nonce tiré une fois par processus (contrainte du SDK), rejeu borné par l'âge maximal de 10 min côté API. Apple proposé **sur iOS seulement** (Android exigerait un flux web avec Services ID). 422 → dialogue de consentement CGU/confidentialité puis rejeu du **même** `id_token` avec `acceptTerms: true`. Annulation dans le SDK → rien. Configuration native (capability Sign in with Apple, schéma d'URL Google iOS, `GOOGLE_SERVER_CLIENT_ID` en `--dart-define` pour Android) à faire avec les identifiants de production (P7-07).
- **Inscription** : case unique CGU + confidentialité obligatoire (ADR-017), langue = langue de l'interface (`fr`/`en`). Contrôles locaux de forme seulement (adresse, 8–128 caractères) ; l'API reste juge.
- **Démarrage** : témoin `.depenseo-installed` dans le dossier de support de l'app ; absent → jetons purgés du trousseau (il survit à la désinstallation sur iOS). Stockage sécurisé illisible → écran « Stockage sécurisé inaccessible » avec nouvel essai manuel (`retry` Riverpod désactivé sur ce fournisseur). Déconnexion : coffre vidé d'abord, `POST /auth/logout` au mieux (hors ligne, le refresh expire seul).

Conséquence : la base locale n'est pas vidée à la déconnexion (aucune donnée synchronisée avant P6-05, qui devra trancher).

## ADR-048 — Verrou de l'app : code à 6 chiffres haché dans le coffre, biométrie en option, surcouche au-dessus du routeur (2026-11-05)

Contexte : P6-03 (F-AUTH-04, NF-SEC-05, MASVS L2). Le cahier des charges fixe « biométrie ou code, délai réglable (immédiat, 1 min, 5 min) » et « captures bloquées sur les écrans sensibles (option), contenu masqué dans le sélecteur d'applications », sans préciser le format du code, le délai par défaut, la limite d'essais ni le cas du code oublié.

- **Code** : 6 chiffres, saisi deux fois, sur un pavé dédié (pas de champ texte). Activer le verrou = choisir un code ; le verrou est actif **si et seulement si** un code est stocké. Stockage : PBKDF2-HMAC-SHA256, 20 000 itérations, sel aléatoire de 16 octets, dans le coffre (Keychain/Keystore, `lock.pin`). Le hachage est une défense en profondeur : 10⁶ codes restent énumérables hors ligne ; la protection réelle est le coffre + la limite d'essais.
- **Essais** : 5 échecs **persistants** (`lock.failures`, survivent au redémarrage) → déconnexion. « Code oublié » → déconnexion après confirmation. La déconnexion (et toute fin de session) efface code, préférences et compteur ; on se reconnecte au mot de passe puis on choisit un nouveau code.
- **Biométrie** : facultative, par-dessus le code (jamais à sa place), `biometricOnly` (le code de l'appareil n'est pas un repli : le code de l'app l'est). Activation soumise à une reconnaissance réussie. Proposée automatiquement à l'affichage de l'écran de verrouillage ; échec ou annulation → code.
- **Délai** : défaut **immédiat** ; compté entre le passage à l'état `hidden` et le retour visible, sur l'horloge murale injectée (`clockProvider`). Horloge reculée pendant l'absence → verrouillé. Démarrage à froid avec un code → verrouillé. Pas de verrou par inactivité au premier plan (non demandé).
- **Affichage** : `LockGate` dans `MaterialApp.builder` : l'écran de verrouillage recouvre le routeur (navigation conservée, contenu `Offstage`, hors arbre sémantique) ; il est **hors Navigator/Overlay** : pas de dialogue ni d'infobulle dedans. Réglages en `/settings` (icône de l'accueil), choix du code en `/settings/pin`.
- **Sélecteur d'apps** (toujours actif) : couverture Flutter dès que l'état n'est plus `resumed` ; iOS : vue native opaque posée sur `UIScene.willDeactivateNotification` (avant l'instantané) ; Android 13+ : `setRecentsScreenshotEnabled(false)`. Android 8–12 : seule la couverture Flutter, non garantie avant l'instantané (limite acceptée ; l'option « bloquer les captures » la couvre via `FLAG_SECURE`).
- **Captures** (option, défaut désactivée) : `FLAG_SECURE` sur toute la fenêtre (toutes les pages connectées affichent des montants : « écrans sensibles » = toute l'app). **Android seulement** : iOS n'a pas d'API de blocage, l'option n'y est pas proposée.
- Android : `MainActivity` hérite de `FlutterFragmentActivity`, thèmes `Theme.AppCompat.DayNight.NoActionBar` (+ dépendance appcompat), permission `USE_BIOMETRIC`. iOS : `NSFaceIDUsageDescription` (fr ; traduction `InfoPlist.strings` à faire en P6-12).

- **Garde** : l'écran de verrouillage ne s'affiche qu'avec une session (`signedIn && (!ready || locked)`) : sans session, rien à protéger et l'écran « stockage inaccessible » reste visible. Contenu masqué : `Offstage` + `ExcludeFocus` ; bouton retour Android consommé sous le verrou (`didPopRoute`). Invite biométrique lancée seulement à l'état `resumed`. Échec compté **avant** la vérification du code. Fin de session → code, préférences et compteur effacés, captures débloquées.
- Non retenu (MVP) : redemander le code avant de désactiver le verrou ; mémoriser `FLAG_SECURE` côté natif (réappliqué par Dart à chaque démarrage) ; PBKDF2 hors du fil UI (`Isolate.run` incompatible avec l'horloge simulée des tests ; ~100 ms par essai).

Conséquence : à vérifier sur appareils réels en recette (P7) : instantané du sélecteur iOS/Android, invite Face ID/empreinte, `FLAG_SECURE`.

## ADR-049 — Saisie rapide mobile : stockage local immédiat, contexte du compte en cache, « aujourd'hui » dans le fuseau du compte (2026-11-05)

Contexte : P6-04 (F-DEP-01 à 03, NF-FMT-04/06). Le cahier des charges ne fixe ni la catégorie ni la date par défaut, ni la présentation des catégories, ni la provenance hors ligne du carnet et de la devise.

- **Tables locales** (Drift, schéma v2, migration additive) : `categories` (champs de la synchro ADR-026) et `expenses` (`id` UUID v7 tiré sur l'appareil par `uuid` 4.6, `amount` entier en unités mineures, `date` `AAAA-MM-JJ`, `tags` tableau JSON, horodatages ISO UTC, `pending_sync` = à envoyer en P6-05). Enregistrer = un `INSERT` local en transaction avec la mémorisation de la dernière catégorie ; aucun appel réseau.

Devise absente de la table ISO figée → indisponible. Préchargé par l'accueil.

Clavier `numberWithOptions(decimal: true)` ; un formateur remplace tout séparateur saisi par celui de la langue (`intl`), « 12.5 » s'affiche « 12,5 » en français.

Sans catégorie locale (avant la première synchro P6-05) : message explicite.

## ADR-050 — Synchro mobile hors ligne : file d'envoi, dernière écriture gagne, déclencheurs sans sonde réseau (2026-11-05)

Contexte : NF-OFF-01 (consultation hors connexion, saisie hors ligne synchronisée sans doublon) ; contrat `GET /sync` (ADR-026), insertion idempotente `POST /expenses` (la première écriture gagne côté API, PATCH « dernier arrivé gagne »). Le cahier ne précise pas la règle de conflit ; PLAN.md impose « dernière écriture gagne » par `updated_at`.

Décision (`mobile/lib/core/sync/sync_engine.dart`, `lib/features/sync/sync_controller.dart`) :
- **Ordre** : purge des autres carnets → envoi de la file → réception. Une synchro à la fois (`SyncController`, demande reçue pendant un passage = un passage de plus).
- **Envoi** : lignes `pending_sync` sans `sync_error`, par `updated_at` croissant. Suppression locale → `DELETE` (404 accepté). Sinon `POST` avec l'UUID v7 de l'appareil : un rejeu (réponse perdue) renvoie la ligne existante identique → simplement acquittée, **jamais de doublon**. Si la ligne renvoyée diffère (elle existait déjà) : la ligne locale porte `base_updated_at`, l'`updatedAt` de la version serveur dont elle part (schéma local v3). Serveur inchangé depuis cette base (ou base nulle = ligne créée ici, réponse perdue) → la modification locale part en `PATCH`, quelle que soit l'avance de l'horloge du serveur. Serveur modifié depuis (conflit réel) → la plus récente par `updatedAt` gagne. 409 (identifiant pris, ou supprimée côté serveur) → ligne gardée, marquée `sync_error = 'conflict'` ; la réception arbitre : suppression distante plus récente → appliquée localement ; sinon la ligne reste en conflit (la restauration d'une dépense supprimée ailleurs puis modifiée ici est laissée à l'utilisateur, P6-06). 400/422 → ligne gardée, marquée `sync_error = 'rejected'`, plus renvoyée tant qu'elle n'est pas modifiée (P6-06 devra effacer `sync_error` à la modification, sans toucher `base_updated_at`). Réseau, 5xx, 403/404 → arrêt, nouvel essai ; 401 → laissé au client HTTP (déconnexion). **Session figée par passage** : après chaque réponse, le marqueur `account.epoch` est relu ; s'il a changé (déconnexion, autre compte), le passage s'arrête sans rien acquitter (un 404 dû au jeton d'un autre compte n'acquitte pas une suppression). Une erreur inattendue (réponse mal formée, défaut du code) est signalée par `FlutterError.reportError` (type et pile seulement) puis traitée comme une indisponibilité.
- **Acquittement conditionnel** : la ligne locale n'est remplacée par la version de l'API que si son `updated_at` n'a pas bougé depuis sa lecture ; une modification faite pendant l'envoi reste en attente.
- **Réception** : pages `GET /sync` (200 lignes) appliquées chacune en transaction ; catégories et dépenses seulement (étiquettes, limites, récurrences : tâches P6-07 à P6-09). Une dépense locale en attente qui l'emporte (même règle que l'envoi) est gardée. `nextUpdatedSince` n'est mémorisé (`sync.v1.<carnet>.since` dans `app_meta`) qu'à la fin du parcours complet : une interruption reprend au point précédent (écritures idempotentes). **410** → synchro complète d'abord, puis retrait des seules lignes synchronisées absentes de cette synchro (par lots de 500) : une coupure pendant la synchro complète n'efface rien. Le préfixe `v1` est le format local : une tâche qui ajoute une table alimentée par la synchro l'incrémente, ce qui force une synchro complète.
- **Changement de compte** (tranche ADR-047/049) : la base n'est pas vidée à la déconnexion ; au premier passage d'un compte, les lignes **déjà synchronisées** des autres carnets et leurs points de reprise `since` sont effacés (elles sont sur le serveur ; un retour du compte refait une synchro complète) ; les saisies jamais envoyées d'un autre compte restent, invisibles (toutes les lectures filtrent par carnet), et partiront si leur propriétaire se reconnecte. Aucune donnée non sauvegardée n'est détruite.
- **Déclencheurs** (pas de `connectivity_plus` : une dépendance de moins, et « réseau présent » ne garantit pas l'API joignable) : contexte du compte prêt (connexion, lancement), après chaque saisie, retour au premier plan, puis nouveaux essais après échec à 15 s, 1 min, puis toutes les 5 min tant que l'app est ouverte. `syncEnabledProvider` coupe la synchro automatique dans les tests widget qui ne l'exercent pas.
- **Consultation hors connexion** : l'accueil liste les 50 dernières dépenses de la base locale (`recentExpenses`, nom de catégorie si connu, icônes « en attente » / « refusée », icône hors ligne dans la barre). Montants affichés par `formatAmount` (entiers seulement, symbole typographique sinon code ISO). La liste complète, la recherche et la modification restent en P6-06.

Limites assumées : une suppression locale part sans arbitrage (elle l'emporte sur une modification faite ailleurs) ; une ligne jamais reçue (`base_updated_at` nul) dont la réponse d'envoi s'est perdue l'emporte sur une modification faite entre-temps sur un autre appareil. Si la ligne est modifiée pendant l'envoi, `base_updated_at` avance quand même sur la version écrite (pas de conflit avec soi-même). Après un 410, le point de reprise n'est écrit qu'après le retrait des lignes absentes. Accueil : icônes distinctes « refusée » et « en conflit ».

Conséquences : en cas de conflit réel (deux appareils), une horloge d'appareil faussée fausse l'arbitrage (accepté : un utilisateur par carnet au MVP). Les saisies non envoyées d'un compte précédent restent dans la base chiffrée de l'appareil (non cloisonnées par utilisateur, jamais affichées) : choix de non-destruction de données non sauvegardées. Le formulaire de saisie ouvert n'est pas rechargé par une synchro (il serait réinitialisé) : les catégories reçues apparaissent à la réouverture.

## ADR-051 — Liste, recherche, modification et suppression annulable sur mobile (2026-11-05)

Contexte : F-DEP-09 (recherche texte, montant, catégorie, période, filtres combinables), F-DEP-10 (modification, suppression annulable 5 s), NF-OFF-01 (consultation hors connexion), §8.1 (recherche insensible à la casse et aux accents). ADR-050 laisse à P6-06 la restauration des lignes en conflit.

Décision (`mobile/lib/core/db/expense_store.dart`, `expense_filter.dart`, `lib/features/expenses/`) :
- **Recherche locale**, pas d'appel à `GET /expenses` : la copie synchronisée suffit et fonctionne hors ligne. Mêmes critères que l'API (ADR-025) : texte sur note **ou** commerçant, montant et période bornes incluses (dates comparées comme chaînes `AAAA-MM-JJ`), plusieurs catégories. Écart assumé : une catégorie racine inclut ses sous-catégories (plus utile sur mobile ; l'API reste exacte). Le pliage casse/accents est fait en Dart (`foldForSearch` : minuscules, table des lettres latines accentuées, `æ/œ/ß`, marques combinantes retirées) car SQLite ne plie que l'ASCII ; les autres critères sont en SQL. Au plus 500 résultats (limite appliquée après le texte). Pas de filtre par étiquette (absent du cahier).
- **Modification** : l'écran de saisie est réutilisé (`/expenses/:id`, champs pré-remplis, devise de la dépense). Toute écriture locale (modification, suppression, restauration acceptée) pose `updated_at` = maintenant, `pending_sync = true`, efface `sync_error`, **garde** `base_updated_at` (ADR-050). La catégorie actuelle reste proposée même masquée.
- **Suppression annulable** : différée, pas défaite. La dépense est masquée tout de suite (`pendingDeletionsProvider`), une SnackBar « Annuler » dure 5 s (`persist: false` : avec une action elle persisterait par défaut) et `deleted_at` n'est écrit qu'à l'expiration. Annuler n'a donc rien à défaire, ni en base ni sur le serveur (aucun DELETE parti puis rattrapé). Changement de session pendant le délai : suppression abandonnée. Limite : une app tuée dans les 5 s perd la suppression (la dépense réapparaît).
- **Conflit** (`sync_error = 'conflict'`, supprimée ailleurs) : bandeau dans l'écran de modification. « Restaurer » appelle `POST …/restore` (en ligne seulement ; échec → message, conflit conservé), puis la ligne repasse en attente et **repose sur la version restaurée** : `base_updated_at` = `updatedAt` renvoyé par l'API (seule écriture qui avance la base : la copie locale part bien de cette version). La synchro la renvoie (POST idempotent puis PATCH, le serveur n'ayant pas bougé depuis la base) quelle que soit l'horloge de l'appareil. « Abandonner » (confirmation) retire la copie locale (la synchro peut ensuite rapporter la version supprimée, sans effet visible). Modifier une ligne en conflit sans la restaurer efface `sync_error` : le prochain envoi reproduit le 409 et le conflit. Un 409 « identifiant pris » (autre carnet) est aussi marqué `conflict` : « Restaurer » y échoue (404, message), seul « Abandonner » s'applique — cas théorique avec des UUID v7.
- **Ligne disparue pendant la modification** (suppression reçue par la synchro) : aucune écriture (les écritures ignorent les lignes à `deleted_at`), message « Cette dépense n'existe plus ». « Annuler » touché après l'expiration (animation de sortie) : message « Trop tard ». Les filtres proposent aussi les catégories masquées.
- Routes à plat `/expenses`, `/expenses/new`, `/expenses/:expenseId` (`new` d'abord). L'accueil ouvre la liste (loupe) et la modification (appui sur une ligne).

## ADR-052 — Gestion des catégories sur mobile, écritures en ligne (2026-11-05)

Contexte : F-CAT-01 (plan France avec sous-catégories, copié par carnet côté serveur, ADR-023), F-CAT-02 (catégories personnalisées : nom, icône, couleur ; masquables). La table locale `categories` (P6-04) n'a ni file d'envoi ni base de conflit ; `CategoryDto` n'expose ni `position` ni `updatedAt`.

Décision (`mobile/lib/core/db/category_store.dart`, `lib/core/categories/category_api.dart`, `lib/features/categories/`) :
- **Lecture locale, écritures en ligne seulement** : création (`POST`, UUID v7 tiré sur l'appareil, rejeu idempotent), personnalisation et masquage (`PATCH` des seuls champs modifiés) passent directement par l'API. Hors ligne (réseau, 5xx, 401, 403, 404 d'une création, changement de session pendant la requête) → message « Connexion requise », rien n'est écrit. L'identifiant d'une création est tiré à l'ouverture du formulaire : un nouvel essai après une réponse perdue rejoue le même `POST` (pas de doublon). Raison : c'est l'option la plus simple et la plus sûre — pas de file d'envoi ni d'arbitrage pour une action rare, pas de dépense locale pointant vers une catégorie inconnue du serveur, pas de suppression par `_forgetUnseen` d'une catégorie jamais envoyée. La saisie de dépenses reste entièrement hors ligne (NF-OFF-01). `syncFormat` inchangé (aucune nouvelle table).
- **Reprise locale** de la réponse : ligne existante mise à jour en gardant `position` et `updated_at` ; nouvelle ligne rangée en dernier, datée de l'horloge de l'appareil. Une synchro est ensuite demandée : elle apporte la ligne serveur complète (l'upsert des catégories est inconditionnel).
- **Écran** `/settings/categories` (depuis Réglages) : racines puis sous-catégories (masquées comprises, signalées et estompées, supprimées et orphelines exclues), interrupteur « proposer à la saisie » par ligne, appui = personnalisation (`/settings/categories/:id`), bouton « + » = création (`/settings/categories/new`, parent facultatif parmi les racines : deux niveaux, ADR-023). Icône = emoji libre (≤ 32 unités UTF-16, limite de l'API), couleur parmi une palette de 14 (`#RRGGBB`), la couleur actuelle hors palette restant proposée. 400/422 (et 409 d'une création : identifiant pris) → « Modification refusée » ; 404/409 d'un `PATCH` → « Cette catégorie n'existe plus ». Une sous-catégorie d'une racine masquée est signalée « non proposée » (comme dans `selectableCategories`). Le formulaire ouvert est lu une fois : une synchro ne l'efface pas.
- **Hors périmètre** : suppression (le masquage couvre F-CAT-02 ; l'API la refuse pour le plan par défaut), déplacement d'une catégorie sous une autre racine, réordonnancement (pas de `position` dans l'API).

Conséquences : personnaliser une catégorie exige le réseau. Une modification faite pendant une synchro en cours peut être brièvement écrasée localement par l'ancienne version reçue ; la synchro demandée ensuite (passage supplémentaire) la rétablit. Pastilles de couleur annoncées par leur code hexadécimal (pas de nom de couleur). Rejeu d'une création après réponse perdue : si le formulaire a été modifié entre-temps, l'API renvoie la première version (la première écriture gagne) et l'écran se ferme ; la correction se fait par une modification. Le formulaire de saisie de dépense ouvert n'est pas rechargé (ADR-050) : une catégorie créée ou réaffichée y apparaît à la réouverture.

## ADR-053 — Limite globale sur mobile, lecture et écriture en ligne (2026-11-05)

Contexte : F-LIM-01/02/03/05/09. L'API calcule périodes, dépensé, restant et pourcentages (ADR-027/028, invariant 8) et versionne la limite (une version par jour, version passée non modifiable). Pas de table locale des limites.

Décision (`mobile/lib/core/limits/`, `lib/features/limits/`) :
- **Tout en ligne** : l'écran `/settings/limits` (depuis Réglages) lit `GET …/limits/current` (jauge) et `GET …/limits` (dernière version, pour préremplir les réglages) ; hors ligne, réseau en échec, 401 ou session changée pendant la requête → « Connexion requise » + « Réessayer ». Raison : l'appareil ne peut pas recalculer la jauge (invariant 8) ; une copie locale périmée serait trompeuse ; c'est l'option la plus simple. La jauge hors ligne relèvera de l'accueil (P6-10, `/dashboard`).
- **Rythme** (F-LIM-03) : « {consumedPercent} % de la limite consommée à {elapsedPercent} % du mois / de la semaine », valeurs de l'API telles quelles ; restant négatif → « Limite dépassée de … ». Sans limite : « Aucune limite définie » + dépensé de la période.
- **Réglages** : type (aucune / mensuelle / hebdomadaire), montant (`parseAmountInput`, devise du compte), jour de début (1–31 pour le mois, lundi–dimanche pour la semaine, lundi par défaut — l'API borne de même), inclusion des récurrences (oui par défaut). « Aucune » envoie `amount: null` en gardant les règles de période et l'inclusion en vigueur. Changer de type remet le jour de début au 1er / lundi, sauf retour au type enregistré.
- **Écriture** (`planLimitWrite`) : réglages identiques → rien ; dernière version datée du jour (`today` de l'API) → `PATCH` des seuls champs modifiés ; sinon `POST` d'une nouvelle version avec un UUID v7 tiré une fois par formulaire (rejeu idempotent). 409 (version créée ailleurs ce jour, version du jour devenue passée après minuit, changement de fuseau) ou 404 d'un `PATCH` → « La limite a changé entre-temps » et rechargement ; 400/422 → « Réglage refusé ». La jauge est rechargée après chaque essai (rechargement en échec : la jauge précédente reste affichée sous un avertissement « Connexion requise », et « Enregistrer » est désactivé jusqu'au rechargement — sinon un rejeu de la même création perdrait la saisie sans le dire) ; le formulaire est recréé (nouvel identifiant) quand la dernière version change.
- **Session** : les données de l'écran portent l'`epoch` de session et le carnet sous lesquels elles ont été lues ; une écriture n'est envoyée, et son succès annoncé, que si l'`epoch` est inchangé avant et après la requête (sinon « Connexion requise »), comme ADR-052.
- Si la dernière version ne s'applique qu'à une période future (`appliesFrom` > aujourd'hui, F-LIM-09), l'écran l'indique (« Ces réglages s'appliquent à partir du … ») ; la jauge en cours garde la limite de l'époque.
- **Hors périmètre** : affichage de l'historique des limites (Premium, P6-13), limites par catégorie (backlog), autres devises (`otherCurrencies` ignoré, devises hors MVP).

Conséquences : consulter ou modifier la limite exige le réseau. Pas de `syncFormat` à incrémenter (aucune table locale).

## ADR-054 — Dépenses récurrentes sur mobile, en ligne (2026-11-05)

Contexte : F-REC-01..04. L'API calcule et matérialise les échéances (ADR-032/033, invariant 8), crée la dépense au paiement avec l'identifiant fourni par le client, et porte les réglages de rappel (par récurrence : J-3 / jour J ; par compte : `reminderTime`, ADR-034). Les tables `recurring_expense` et `occurrence` sont dans la synchro, mais l'app n'a pas de table locale pour elles.

Décision (`mobile/lib/core/recurring/`, `lib/features/recurring/`) :
- **Tout en ligne**, comme ADR-052/053 : écran `/settings/recurring` (depuis Réglages) qui lit `GET …/recurring-expenses`, puis `GET …/{id}/occurrences` de chaque récurrence (en parallèle), puis `GET /me` (`reminderTime`). Raison : option la plus simple ; pas de calcul d'échéance sur l'appareil ; pas de nouvelle table locale ni de `syncFormat` à incrémenter. Le nombre de récurrences d'un carnet est faible (N+1 requêtes acceptables) ; une route d'échéances par carnet pourra les remplacer. La liste hors ligne des prochaines échéances relèvera de l'accueil (P6-10, `/dashboard`).
- **Échéances** : seules les `pending` sont affichées, par date puis nom ; « À confirmer » si `awaitingConfirmation` ; montant estimé préfixé « ≈ ». Aucune mention « en retard » calculée sur l'appareil.
- **Actions** (feuille du bas) : « Payer » (« Confirmer » si à confirmer : même route `POST …/pay`, F-REC-02) avec un UUID v7 de dépense tiré **une fois par échéance** et gardé en mémoire (rejeu idempotent après réponse perdue), puis demande de synchro pour rapatrier la dépense ; « Ajuster le montant » (`PATCH …/occurrences/{id}` `{amount}`) et « Revenir au montant prévu » (`{amount: null}`) si ajustée ; « Sauter » après confirmation. Payer un montant différent = ajuster puis payer (pas de champ montant/date au paiement).
- **Formulaire** : nom, montant (devise du compte), fixe / estimé, fréquence, première échéance (aujourd'hui dans le fuseau du compte par défaut), catégorie, « Enregistrer automatiquement » (mode `auto`, sinon `confirm` par défaut), rappels J-3 et jour J (le second masqué en mode automatique, sans effet, ADR-034). Création : `POST` complet avec UUID v7 tiré une fois par formulaire ; modification : `PATCH` des seuls champs changés (rien si aucun) ; fréquence et première échéance affichées mais figées (immuables côté API). Suppression après confirmation (`DELETE`, échéances en attente supprimées, dépenses conservées).
- **Heure des rappels** : réglage commun du compte (`PATCH /me {reminderTime}`), au sélecteur d'heure, sur le même écran. Les autres réglages de notification (types, plage de silence, rappel quotidien) relèvent de P6-11.
- **Erreurs** : 400/422 → « Refusé : vérifiez les champs » ; 404/409 → « ont changé entre-temps » + rechargement ; réseau, 5xx, 401, réponse illisible ou session changée (`epoch`, comme ADR-052/053) → « Connexion requise ». Rechargement en échec : liste affichée sous l'avertissement, actions désactivées.

Conséquences : gérer les récurrences exige le réseau ; la dépense payée apparaît localement après la synchro.

## ADR-055 — Accueil mobile et graphiques (2026-11-05)

Contexte : F-TB-01/02. L'API fournit tout le tableau de bord en une requête (`GET …/dashboard`, ADR-031 : jauge, 5 prochaines échéances, 5 dernières dépenses, répartition par catégorie racine, cumuls courant/précédent par rang de jour, 12 périodes). Invariant 8 : aucun calcul sur l'appareil. L'accueil existant affiche la copie locale des dépenses (hors ligne, NF-OFF-01).

Décision (`mobile/lib/core/dashboard/`, `lib/features/home/`) :
- **Indicateurs en ligne** : jauge (`LimitSummaryCard` réutilisée), prochaines échéances (« En retard » = champ `overdue` de l'API ; toucher → écran des récurrences pour payer/sauter), répartition (anneau fl_chart + légende nom/montant/%), cumul (deux courbes + phrase « X à ce jour, contre Y au même jour de la période précédente »), évolution (12 barres, la dernière = période en cours). Le « même jour » est **lu** dans `cumulative.previous` (point de rang ≤ dernier rang courant), pas calculé.
- **Dernières dépenses : copie locale**, pas `recent` de l'API. Raison : disponibles hors ligne, incluent les saisies non synchronisées et restent modifiables/supprimables (P6-06). Le champ `recent` est ignoré.
- **Rafraîchissement et hors ligne (NF-OFF-01)** : au chargement de l'accueil, après chaque synchro **réussie** (les données envoyées sont prises en compte), et par « Réessayer ». Chaque réponse lue est gardée brute dans `app_meta` (`dashboard.v1.<carnet>`, base chiffrée ; purgée avec les autres carnets par la synchro, ADR-050). API injoignable ou réponse illisible : dernière réponse gardée affichée sous l'avertissement « Connexion requise » (indicateurs du jour de cette réponse, non recalculés). Pas d'indicateur animé pendant le chargement (liste locale et « + » utilisables aussitôt).
- **Noms et couleurs des catégories** : copie locale (`filterableCategories`) ; identifiant inconnu (supprimée, pas encore synchronisée) → « Catégorie indisponible » en gris.
- **Devises** : la comparaison au cumul précédent n'est affichée que si la période précédente (`evolution`, avant-dernière) est dans la devise de la jauge (ADR-031 : devise de chaque version de limite). `gauge.otherCurrencies` n'est pas affiché (devises hors MVP).
- **Montants** : `double` uniquement comme coordonnées de tracé fl_chart ; tout texte affiché ou lu (légende, résumé, libellé d'accessibilité) passe par `formatAmount` sur les entiers. Interactions fl_chart (infobulles) et titres d'axes désactivés : ils formateraient des `double`.
- **Accessibilité** : canevas exclus de l'arbre sémantique ; équivalents textuels visibles (légende, phrase de cumul, bornes des 12 périodes) ; le graphique d'évolution porte un libellé listant « période : montant », la dernière marquée « (en cours) » (aussi distinguée par la couleur `primary`, les autres en `outline`).
- Session changée (`epoch`) pendant la requête → ni affichage ni copie. Réponse illisible → jamais affichée (copie précédente si elle existe).

Conséquences : `fl_chart` ^1.3.0 ajouté. Hors ligne, les indicateurs affichés sont ceux de la dernière réponse reçue (période éventuellement révolue), signalés comme tels.

## ADR-056 — Notifications push sur mobile : jeton, appareil, réglages (2026-11-05)

Contexte : P6-11 (F-NOT-01, 02, 04, 05). L'API (ADR-034/035) envoie elle-même à FCM (HTTP v1, `message.token`) et à APNs (jeton d'appareil brut) ; le cahier ne dit rien du moment de la demande d'autorisation, ni de la configuration Firebase, ni du lien entre l'interrupteur « rappel quotidien » et `dailyReminderTime`.
Décision :
- Jeton : `firebase_core` 4.15.2 + `firebase_messaging` 16.7.1 derrière l'interface `PushService` (`lib/core/push/`). Pas la ligne 5.x/17.x : elle tire firebase-ios-sdk 13, incompatible (SPM) avec GoogleSignIn-iOS 9 de `google_sign_in_ios` 6.3.8 (dernière version) ; en 17.x, `getToken` est en outre déprécié au profit d'un FID (`register()`/`onRegistered`), cible que l'API ne gère pas. Android : jeton d'enregistrement FCM (`getToken`) ; iOS : jeton APNs brut (`getAPNSToken`, 5 essais à 1 s). Configuration Firebase **par `--dart-define`** (`FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_ANDROID_APP_ID`, `FIREBASE_IOS_APP_ID`, `FIREBASE_IOS_BUNDLE_ID`), aucun `google-services.json`/`GoogleService-Info.plist` dans le dépôt ; absente (CI, développement) → `DisabledPushService`, rien n'est demandé ni envoyé.
- Autorisation demandée à l'ouverture de session (et à chaque démarrage connecté, l'OS ne redemande pas après un choix). Refus → aucun enregistrement ; les réglages restent modifiables.
- Appareil : UUID v7 tiré une fois, conservé dans le coffre (`push.v1.device_id`, survit à la déconnexion) ; `PUT /me/devices/:id` à chaque ouverture de session/démarrage connecté et à chaque nouveau jeton ; 409 (identifiant resté sur un autre compte) → nouvel identifiant et un nouvel essai. Au mieux : une erreur est ignorée, retentée au démarrage suivant ; jeton jamais journalisé. Opérations sérialisées.
- Déconnexion : `DELETE /me/devices/:id` **avant** d'effacer les jetons, hors de la file d'enregistrement (un dialogue d'autorisation en attente ne la retarde pas), borné à 5 s, erreurs ignorées ; un nouveau jeton reçu pendant ou après la déconnexion n'est plus envoyé jusqu'à la session suivante. Retrait impossible (session expirée, hors ligne, délai dépassé) : l'appareil reste rattaché au compte quitté jusqu'à la connexion suivante (l'API rattache alors le jeton au nouveau compte, ADR-035) et peut recevoir des notifications génériques sans montant — accepté au MVP.
- Limites acceptées : sur iOS, `onTokenRefresh` signale le jeton FCM, pas l'APNs ; un changement de jeton APNs n'est rattrapé qu'au démarrage suivant. L'autorisation peut être demandée alors que l'écran de verrouillage de l'app est affiché (dialogue système au-dessus).
- Réglages (`/settings/notifications`) **en ligne seulement**, lus à chaque ouverture : quatre interrupteurs, chacun envoyant son seul champ en `PATCH /me/notification-settings`. « Rappel quotidien » affiché actif si `dailyReminder` **et** `dailyReminderTime` non nul ; l'activer pose l'heure (conservée, sinon **20:00**) et réactive le type s'il était coupé ; le désactiver met `dailyReminderTime` à `null`. Plage de silence : activation à **22:00–07:00**, bornes modifiables, début = fin refusé localement. Échec → message, état précédent conservé. Mention « aucun montant » (F-NOT-05, ADR-003).
- Sélecteur d'heure en saisie : la saisie est alignée sur le format affiché par la langue (bogue Flutter : en fr sans 24 h imposé par l'appareil, « 07 » saisi depuis 20:00 donnait 19:00).
- Premier plan : pas de `flutter_local_notifications` ; une notification reçue app ouverte n'est pas affichée sur Android (comportement FCM par défaut) — accepté au MVP.
Conséquences : à vérifier sur appareil Android (P7-07) : réception d'une notification app tuée avec Firebase initialisé seulement depuis Dart ; en cas d'échec, générer `google-services.json` au build (non committé) et appliquer le plugin Gradle `google-services` s'il est présent. Publication (P7-07) = projet Firebase + clé APNs, capability Push Notifications (`aps-environment`) et mode d'arrière-plan `remote-notification` côté iOS, dart-defines Firebase en build de release.

## ADR-057 — Écran Compte mobile : exports, suppression, documents légaux (2026-11-05)

Contexte : P6-12 (F-EXP-01, F-AUTH-07, F-AUTH-08, §6). L'API produit les exports en tâche de fond (ADR-036/038, 202 puis état puis fichier) et supprime le compte immédiatement (ADR-037) ; le cahier ne dit ni comment remettre le fichier, ni la forme de la confirmation, ni où vivent les textes légaux.
Décision :
- Écran `/settings/account` **en ligne seulement** : export des dépenses (période par défaut = du 1er du mois au jour courant **dans le fuseau du compte**, bornes modifiables, début > fin refusé localement ; format CSV ou « Excel (Premium) » : l'app ne connaît pas encore le plan (P6-13), le 403 de l'API à la création d'un export Excel est traduit en message « réservé au Premium », le CSV reste gratuit ; dates choisies au plus tard aujourd'hui), export des données personnelles (zip), lien vers les documents légaux, suppression du compte.
- Export : nouvel UUID v7 par demande, `POST` puis interrogation de l'état (2 s, 3 s, 5 s puis 10 s, ~5 min au total : la file est traitée chaque minute par le cron) tant que l'écran est ouvert (écran quitté → `ExportCancelled`, plus aucune requête) ; `failed`/`expired`/toujours `pending` → message « réessayez plus tard ». Pas de reprise d'une demande après fermeture de l'écran (simplicité ; une nouvelle demande suffit).
- Remise du fichier : téléchargement en octets puis **feuille de partage du système** (`share_plus` 13.3.1, derrière `FileSharer`) ; copie en clair écrite dans `cache/exports/`, vidé avant chaque export, à la déconnexion, à l'expiration de session et à la suppression du compte. Noms : `depenseo-<du>-<au>.csv|xlsx`, `depenseo-donnees-<jour>.zip`.
- Suppression : dialogue de confirmation exigeant la saisie de `SUPPRIMER` (`DELETE` en anglais, casse et espaces ignorés), rappel de l'irréversibilité et de l'export préalable ; pas de ressaisie du mot de passe (ADR-037, comptes sociaux). Après 204 : `AuthController.accountDeleted()` — identifiant d'appareil oublié et réenregistrement bloqué, jetons effacés **sans** `POST /auth/logout` ni `DELETE /me/devices` (déjà supprimés), marqueur `account.epoch` effacé puis **attente de la fin du passage de synchro en cours** (`SyncController.settled`, passé par l'écran : la synchro dépend de la session), copies d'export effacées, **toutes les tables locales vidées** (`AppDatabase.wipeAll`, la base et sa clé restent) ; chaque étape au mieux, déconnexion dans tous les cas (la synchro de la connexion suivante purge les autres carnets). Reste accepté : un rafraîchissement du contexte du compte ayant passé son contrôle de marqueur juste avant l'effacement peut réécrire `account.*` dans `app_meta` (métadonnées seules, écrasées à la connexion suivante). Verrou de l'app (code, préférences) conservé : réglage de l'appareil.
- Documents légaux (§6) **embarqués** dans l'app (`lib/features/account/legal_texts.dart`, fr + en), lisibles hors ligne : mentions légales (dont licences SQLCipher/OpenSSL, ADR-046), confidentialité (contact données personnelles, droits, CNIL), CGU, CGV (prix TTC, renouvellement, résiliation), déclaration d'accessibilité (WCAG 2.1 AA visé, partiellement conforme). Identité de l'éditeur et adresse de contact par `--dart-define` `LEGAL_PUBLISHER` / `LEGAL_CONTACT_EMAIL` (sinon mention « à compléter » ; **une build de release refuse de démarrer** si l'un manque, `checkLegalConfig`). Sous-traitants hors UE cités de façon générique (FCM, APNs, connexion Apple/Google, e-mails) ; pas de clause de rétractation (à trancher par le juriste) ; médiateur de la consommation renvoyé aux mentions légales (`LEGAL_PUBLISHER`). Prix Premium écrits dans les CGV (§5, hypothèses) : un changement de prix impose une mise à jour de l'app. Page « Licences des logiciels » = `showLicensePage` Flutter, avec SQLCipher et OpenSSL ajoutés au `LicenseRegistry` au démarrage.
Conséquences : avant publication (P7-07) : faire valider les textes par un juriste (§6), définir les deux dart-defines en release, vérifier le texte de licence SQLCipher/OpenSSL contre la build embarquée. `share_plus` tire `url_launcher` en dépendance transitive (aucun usage direct).

## ADR-058 — Premium sur mobile : achats intégrés, essai, restauration, lecture seule (2026-11-05)

Contexte : P6-13 (F-ABO-01, 02, 03, §5). L'API tranche les droits (ADR-040/041 : `GET /subscriptions`, `POST /subscriptions/trial`, `POST /subscriptions/verify`) ; le cahier ne fixe ni le parcours d'achat dans l'app, ni la conduite à tenir quand la vérification échoue, ni l'affichage des échéances.
Décision :
- **Aucun droit calculé par l'app** : l'état vient de `GET /subscriptions` (`subscriptionStatusProvider`, relu à chaque changement de compte, sans nouvel essai automatique) ; un achat n'est accordé qu'après le 200 de `/subscriptions/verify`.
- Store derrière `StoreGateway` (`lib/core/premium/`) : `InAppPurchaseGateway` (in_app_purchase 3.3.1, StoreKit 2 par défaut sur iOS, Play Billing sur Android), `UnavailableStoreGateway` ailleurs, `FakeStore` en test. Preuve : `purchaseID` (identifiant de transaction StoreKit 2) → `{store: 'app_store', transactionId}`, `serverVerificationData` (jeton d'achat Play) → `{store: 'google_play', purchaseToken}`. L'identifiant du compte Depenseo (UUID) est passé en `applicationUserName`, que le plugin transmet en `appAccountToken` (iOS) et `obfuscatedAccountId` (Android) : l'API peut ainsi refuser (409) l'achat d'un autre compte (ADR-040). Achat par `buyNonConsumable` (méthode du plugin pour les abonnements).
- `PurchaseHandler` (`lib/features/premium/premium_providers.dart`), écouté dès le démarrage de l'app (`purchaseListenerProvider`, comme le recommande le plugin) ; achats traités en série. `purchased`/`restored` : attendre l'état de session ; hors session, rien n'est présenté ni clos (redélivré à la prochaine ouverture). 200 → transaction close (`completePurchase` : accusé de réception Play sous 3 jours, `finish` StoreKit), état relu. 400 (reçu invalide) et 409 (autre compte) → close, message. Hors ligne, 503 ou autre erreur → **laissée ouverte** (message « sera retentée ») puis **reprise** par `StoreGateway.unfinished()` à l'ouverture de session et à chaque retour au premier plan (Android : `queryPastPurchases` non acquittés — Play ne redélivre pas un achat non acquitté et le rembourse sous 3 jours ; iOS : `Transaction.unfinished`, clos par `finish`), où les droits sont aussi relus (fin d'essai ou d'abonnement en cours de session). Sur iOS, une transaction non close au lancement peut être présentée deux fois (flux `updates` + reprise) : la vérification est idempotente côté API ; un achat déjà clos pendant l'exécution (même preuve, statut `purchased`, ex. retour de la feuille d'achat qui déclenche aussi la reprise) est clos sans nouvelle vérification. Appareil partagé : un achat du compte A repris sous le compte B reçoit 409 et est clos ; A récupère ses droits par « Restaurer ». Un paiement Play différé (`pending`) repris réaffiche « en attente » à chaque retour au premier plan si l'écran est ouvert. `pending` → message ; `canceled`/`error` → close.
- Écran `/settings/subscription` (entrée « Abonnement » de l'écran Compte, avec le libellé de l'offre) : état (« Offre gratuite », « Essai Premium jusqu'au <dernier jour> inclus » = date locale de `trialEndsAt − 1 ms` dans le fuseau du compte, puisque la fin est minuit au début du jour 15 ; « Premium jusqu'au <date locale de premiumUntil> »), bouton d'essai si `trialAvailable` (sans store ni moyen de paiement ; 409 → message et état relu), produits du store avec leurs **prix localisés fournis par le store** (aucun prix codé dans l'app), « Restaurer mes achats » (`restorePurchases`, les achats redélivrés passent par le même traitement), « Gérer ou résilier l'abonnement » toujours affiché quand un store existe, même si `GET /subscriptions` échoue (avec « Restaurer ») : lien externe (`url_launcher`) vers `https://apps.apple.com/account/subscriptions` ou `https://play.google.com/store/account/subscriptions?package=fr.depenseo.depenseo` (§5 : résiliation en un clic vers le store ; l'app ne résilie rien elle-même). Achat masqué en Premium ; possible pendant l'essai. Play : une entrée par produit (forfait de base, offre sans `offerId`). Restauration sans achat trouvé : seul le message « Recherche de vos achats… » s'affiche (le plugin ne signale pas une restauration vide).
- Multi-appareils (F-ABO-03) : l'état est lié au compte ; un autre appareil connecté au même compte voit Premium sans achat ni restauration.
- Lecture seule à expiration (§5, ADR-041) : sur l'écran Compte, si l'API dit `free`, l'option « Excel (Premium) » est désactivée avec la mention « Export Excel réservé à Premium. » et l'export part en CSV ; rien n'est effacé localement. État inconnu (hors ligne, erreur) : option laissée active, le 403 de l'API reste expliqué (ADR-057).
Conséquences : avant publication (P7-07) : créer `premium_monthly`/`premium_yearly` dans App Store Connect et la Play Console **sans offre d'introduction** (ADR-040), activer la capacité In-App Purchase dans Xcode, tester en bac à sable (StoreKit Configuration, testeurs de licence Play). Changement d'offre mensuelle ↔ annuelle : géré par le store (lien de gestion), pas par l'app.

## ADR-059 — Dates sur mobile : affichage et tests multi-fuseaux (2026-11-05)

Contexte : P6-14 (NF-FMT-02, 03, 05). Les conversions `AAAA-MM-JJ` ↔ `DateTime` étaient recopiées dans cinq écrans ; rien ne vérifiait que le résultat ne dépend pas du fuseau de l'appareil. NF-FMT-03 veut les horodatages techniques « affichés dans le fuseau de l'appareil ».
Décision :
- Un seul module `lib/core/dates/date_display.dart` : `parsePlainDate` (chaîne stricte → `DateTime` local à minuit, réservé aux sélecteurs de date ; `FormatException` si la chaîne ou la date est invalide), `formatCalendarDate(date, locale, {long})` (chaîne validée et lue en composantes UTC puis `DateFormat` : aucun décalage possible, même là où minuit local n'existe pas ; chaîne invalide = affichée brute pour ne pas casser une liste), `formatInstantDate(timeZone, instant, locale)` = `todayIn` puis `formatCalendarDate`. Relecture d'une date choisie : `formatPlainDate` (composantes, sans conversion). Interdit : `DateTime.parse('AAAA-MM-JJ')` sur une date calendaire.
- Aucun horodatage technique (création, modification) n'est affiché par l'app aujourd'hui : NF-FMT-03 est sans objet côté affichage. Les échéances d'abonnement (`trialEndsAt`, `premiumUntil`) sont des bornes de droits : affichées comme **jour calendaire dans le fuseau du compte** (comme toutes les périodes calculées par l'API, NF-FMT-04), pas de l'appareil. Un futur affichage d'horodatage technique utilisera `toLocal()`.
- Tests : étiquette `tz` (`mobile/dart_test.yaml`) sur les tests de dates purs (`test/dates/`) et les tests widget multi-fuseaux (saisie rapide, échéances Premium) ; `mobile/tool/test_tz.sh` les rejoue sous `TZ=Europe/Paris`, `Europe/Lisbon`, `America/Montreal`, `Indian/Reunion` (fuseau de l'**hôte**), en plus des 4 fuseaux de **compte** couverts dans chaque test, y compris les instants qui encadrent les changements d'heure 2026 (Europe 29 mars / 25 oct., Montréal 8 mars / 1er nov.). Lancé en CI après `flutter test`.
Conséquences : tout nouveau calcul ou affichage de date mobile passe par `today.dart` / `date_display.dart` et ajoute un test étiqueté `tz`. Le `_today` des formulaires (saisie, compte, récurrence) reste figé à l'ouverture de l'écran (accepté : un écran ouvert au passage de minuit garde la veille par défaut).

Contexte : P7-01 (§11.1). Environ vingt chemins de `docs/dev/TRACEABILITY.md` étaient « prévus » mais faux (fichiers renommés, noms sans répertoire, motifs). Une vérification manuelle aurait dérivé de nouveau.

## ADR-061 — Périmètre et contrôle de la couverture (2026-11-05)

Contexte : P7-02 (NF-QUA-01, CLAUDE.md « ≥ 70 % sur `domain/` et `services/` »). Ni l'API ni le mobile n'ont de dossiers `domain/`/`services/` : le code est découpé par fonctionnalité (`src/limits/`, `lib/features/…`).
Décision : interprétation la plus simple et la plus stricte — le seuil s'applique à **tout** le code source, hors point d'entrée et code généré.
- API : `@vitest/coverage-v8` 5.1.0 (aligné sur vitest), `coverage.include = src/**/*.ts` sauf `src/main.ts`, seuil 70 % sur lignes, instructions, fonctions et branches ; le script `test` de l'API lance `vitest run --coverage`, donc `pnpm test` local et CI échouent sous le seuil. Mesure initiale : 97 % lignes, 88 % branches. Une exécution partielle passe par `pnpm --filter api exec vitest run <fichier>` (sans couverture : le seuil global échouerait sur un sous-ensemble).
- Mobile : `flutter test --coverage` en CI puis `node scripts/lcov-threshold.mjs mobile 70` : 70 % des lignes de `lib/` hors `*.g.dart`, `*.freezed.dart`, `lib/l10n/`. Comme lcov omet un fichier qu'aucun test ne charge, tout fichier de `lib/` absent du rapport fait échouer le contrôle, sauf `lib/main.dart` (point d'entrée, non chargé par les tests) et `lib/core/clock.dart` (`typedef` seul). Mesure initiale : 92,55 %.
- Délai de la suite de sauvegarde/restauration porté à 30 s (sous instrumentation v8, elle dépasse 5 s) ; les autres tests gardent 5 s pour qu'un ralentissement reste visible.
- Outillage : `scripts/tsconfig.json` (`allowJs`, sans `checkJs`) fournit un projet aux scripts racine pour eslint, dont le projet par défaut est limité à 8 fichiers.
Conséquences : un nouveau fichier mobile doit être chargé par au moins un test. `packages/shared` garde son script `coverage` facultatif (hors seuil, hors périmètre de la tâche).

## ADR-062 — Limitation de débit de `/auth` et en-têtes de sécurité (2026-11-05)

Contexte : P7-03 (NF-SEC-01, NF-SEC-04). Le cahier ne fixe ni seuils ni en-têtes (« à définir plus tard », l. 379) ; ADR-017/018/019 renvoyaient la limitation à cette tâche. Passenger lance plusieurs processus sans mémoire partagée, et o2switch n'offre aucun service permanent (Redis…).
Décision :
- Compteur **en base**, table `rate_limit` (migration 0019) : clé = HMAC-SHA-256 de « portée + valeur » (`BINARY(32)`, clé dérivée de `JWT_ACCESS_SECRET` : une IPv4 ou un e-mail ne se retrouvent pas par force brute ; donnée pseudonyme), fenêtre fixe de 15 min ouverte par la 1re tentative, `INSERT … ON DUPLICATE KEY UPDATE` **écrit en SQL brut** (Drizzle émet les affectations dans l'ordre des colonnes de la table ; `window_started_at` affectée en dernier pour que les deux conditions lisent sa valeur d'origine, indépendamment de `SIMULTANEOUS_ASSIGNMENT`) puis relu dans la même transaction. Toute tentative compte, réussie ou non, et dans chaque seau même si un autre refuse. `Retry-After` borné à [1, 900] s. Purge `purge-expired-rate-limits` dans les tâches planifiées. Table hors export RGPD et hors suppression (`UNLINKED_TABLES`, colonnes figées par le test), clé primaire naturelle `bucket` (exception nommée dans `schema-invariants.ts`).
- Garde `@RateLimited()` (`src/rate-limit/rate-limit.guard.ts`) posée sur `register`, `verify-email`, `login`, `social`, `password-reset/request`, `password-reset/confirm` : **30 appels / 15 min par IP** (`AUTH_RATE_LIMIT_PER_IP`), plus **10 / 15 min par adresse e-mail** sur `login` (`AUTH_RATE_LIMIT_PER_ACCOUNT`, normalisée comme `emailSchema`). Au-delà : 429 `application/problem+json` + `Retry-After` (secondes). `refresh` et `logout` ne sont pas limités (jeton aléatoire de 256 bits). Le back-office garde son propre compteur d’échecs (`src/admin/admin-login.service.ts`).
- Adresse cliente : `TRUST_PROXY_HOPS` → `trust proxy` d'Express, **obligatoire en production** (démarrage refusé sinon) : derrière Passenger, l'adresse TCP est celle du proxy et tous les clients partageraient un seau qu'un tiers saturerait en 30 requêtes. Valeur à établir en P7-07 selon le proxy o2switch, **en vérifiant sur le serveur que `req.ip` est bien l'adresse du client** (et non `127.0.0.1` : avec un mauvais réglage, tous les clients partageraient un seau). Hors production, 0 par défaut. Adresse inconnue (socket Unix) : pas de seau IP (seul le seau par compte s'applique). Les tests neutralisent les seuils dans `TEST_ENV` et les fixent dans `test/security/rate-limit.spec.ts`.
- En-têtes posés par un middleware maison (`src/http/security-headers.ts`, pas de helmet) sur toute réponse : HSTS `max-age=31536000; includeSubDomains` (sans `preload`, difficilement réversible ; `includeSubDomains` s'applique à tous les sous-domaines si l'API est servie sur le domaine racine : à vérifier en P7-07), CSP `default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, COOP et CORP `same-origin`. Les pages du back-office remplacent la CSP par `CONSOLE_CSP` (ADR-044).
- Auto-évaluation MASVS L2 : `docs/dev/MASVS.md`. Écart accepté : pas d'épinglage de certificat (NETWORK-2), car les certificats Let's Encrypt d'o2switch tournent tous les 90 jours et un épinglage périmé couperait toutes les installations. Les autres écarts sont listés en fin de document, à traiter en P7-07/P7-08.
Conséquences : verrouillage par compte = déni de service possible sur un compte ciblé, borné à 15 min (accepté, l'utilisateur garde la connexion Apple/Google). Le partage d'IP (NAT d'entreprise, CGNAT mobile) peut bloquer plusieurs utilisateurs légitimes au-delà de 30 appels / 15 min : seuil à réévaluer avec les journaux de production.

## ADR-064 — Suivi des erreurs Sentry, région UE, sans montant ni PII (2026-11-05)

Contexte : P7-05 (NF-QUA-02, NF-SEC-06, §8.1 « Sentry (hébergement UE) »). Le cahier ne précise ni la manière de garantir la région ni le contenu admis dans un événement.
Décision :
- **Région UE imposée par la configuration** : `SENTRY_DSN` (API, variable d'env) et `--dart-define=SENTRY_DSN` (mobile) n'acceptent qu'un DSN `https://clé@….de.sentry.io/…` (ingestion Francfort) ; tout autre DSN = démarrage refusé. Absent ou vide = aucun envoi (dev, tests, CI). `SENTRY_ENVIRONMENT` (dev/recette/prod ; mobile : `production` en release, `development` sinon), `SENTRY_RELEASE` (API, ex. SHA). Organisation Sentry à créer **dans la région UE** (choix définitif à la création, P7-07).
- **API** (`@sentry/node` 11.11.0, `src/observability/sentry.ts`) : `Sentry.init` dans `main.ts` seulement (pas dans `createApp` : tests et cron n'envoient rien). Intégrations listées une à une (exceptions/rejets non gérés, erreurs liées, déduplication) : ni HTTP, ni console, ni OpenTelemetry, ni injection de canaux ; `dataCollection` tout à faux (Sentry 11 remplace `sendDefaultPii`), `includeServerName: false`. Les 5xx inattendues sont signalées par `ProblemDetailsFilter` (une `ProblemException` 5xx est voulue, ex. 503 « non configuré » : non signalée). `beforeSend` = `scrubEvent`, événement **reconstruit par listes blanches** (un champ ajouté par une future version du SDK ne part pas) : type d'erreur, `mechanism` réduit à `type/handled/synthetic`, pile **sans** variables ni lignes de source, méthode, chemin **sans** paramètres, en-têtes `content-type/length`, `accept`, `user-agent`, contextes du SDK (`runtime`, `os`, `device`, `app`, `culture`, `cloud_resource`, `trace`). Retirés : message, `logentry`, valeur des exceptions et de leurs `cause` (comme `describeError`), utilisateur, `extra` (le SDK y recopie un objet non-`Error` lancé), tags, corps, cookies. Fils d'Ariane : sans message, données passées à `redactDeep`, URL sans paramètres.
- **Mobile** (`sentry_flutter` 10.3.0, `lib/core/observability/sentry_config.dart`) : `SentryFlutter.init` dans `main.dart` si DSN ; suivi automatique des sessions gardé (taux de sessions sans plantage = mesure de NF-QUA-02) ; pas de traces de performance, ni capture d'écran, ni arbre de vues, ni fils d'Ariane `print`/interactions/natifs. `beforeSend` = `scrubSentryEvent` : retire message, valeur des exceptions, requête, `extra`, nom de l'appareil, contextes et tags non standard ; ne garde de `flutter_error_details` que `library` (`context`/`information` décrivent les widgets, donc les textes affichés) ; utilisateur réduit à l'identifiant d'installation pseudonyme du SDK.
- Les erreurs **natives** (exceptions Java/Kotlin des plugins — SQLCipher, local_auth, share_plus… —, `NSException` iOS, plantages NDK) sont envoyées par le SDK natif **sans** passer par `beforeSend` Dart : leur message peut porter une valeur. On garde la gestion native (sinon le taux de sessions sans plantage de NF-QUA-02 serait faux) et on impose un **nettoyage côté serveur**, réglage du projet Sentry obligatoire à la mise en service (check-list P7-07) : *Data Scrubber* et *Use Default Scrubbers* actifs, *Prevent Storing of IP Addresses* actif, règles *Advanced Data Scrubbing* « Remove — Anything — `$error.value` » et « Remove — Anything — `$message` », rétention minimale. Ces réglages valent aussi pour l'IP que Sentry déduirait côté serveur (sessions, événements natifs) : condition de NF-SEC-06 qu'aucun test ne vérifie.
- Politique de confidentialité embarquée : Sentry ajouté aux sous-traitants (hébergé dans l'UE).
Conséquences : un diagnostic ne dispose jamais du message d'erreur ; s'appuyer sur le type, la pile et le chemin. Toute nouvelle intégration Sentry (HTTP, Dio, navigation) doit passer par une relecture NF-SEC-06. Le script cron (`jobs-run`) n'est pas instrumenté (ses échecs restent dans la table `job` et les journaux) ; à reconsidérer si besoin.

## ADR-065 — Mesure de performance : banc autocannon et démarrage mobile (2026-11-05)

Contexte : P7-06 (NF-PERF-01, NF-PERF-02). Le cahier fixe les cibles (p95 < 300 ms, accueil < 2 s sur un téléphone milieu de gamme de 2023) mais ni la charge, ni les routes, ni l'environnement de mesure.
Décision :
- **API** : banc Vitest séparé (`apps/api/bench/p95.bench.ts`, `vitest.bench.config.ts`, `pnpm --filter api bench`, autocannon 8.0.0) hors `pnpm test` et sans couverture (l'instrumentation fausserait les durées), lancé en CI après `pnpm test`. Application complète écoutant sur un port local, journal pino conservé mais jeté. 7 routes clés (accueil, liste, recherche, synchro complète, catégories, limites en cours avec 12 périodes passées, saisie) sur 10 000 dépenses et une limite globale à deux versions, 4 connexions × 5 s par route après 10 appels de chauffe (le premier appel après veille est exclu par NF-PERF-02). Seuil : p95 **par route** < 300 ms (plus strict qu'un p95 global), aucune erreur, au moins 50 appels. p95 calculé exactement sur chaque réponse.
- **Mobile** : `integration_test` sur l'application complète avec API simulée sans délai et vraie base SQLCipher ; mesure du premier rendu à l'accueil affiché. Budget de 2 s imposé seulement hors debug (`flutter drive --profile` sur téléphone) ; en debug/simulateur, valeur relevée. Pas en CI (aucun appareil sur l'exécuteur Linux).
Conséquences : la CI garantit une régression grossière côté API, pas la performance sur o2switch (Passenger, CPU partagé) : mesure de recette à faire à la mise en service (P7-07). Mesures locales faites sous Node 26 ; la CI tourne sous Node 22. La mesure mobile n'inclut ni le coffre réel, ni une base remplie, ni le travail avant `runApp` (détail dans `PERF.md`). La cible NF-PERF-01 reste **non vérifiée sur appareil** tant que la ligne « téléphone milieu de gamme 2023 » de `docs/dev/PERF.md` n'est pas remplie.

## ADR-066 — Données fictives hors production et déploiement (2026-11-05)

Contexte : P7-07 (NF-QUA-03 : « données fictives hors production »). Le plan cite `scripts/seed-fake.ts` à la racine ; les scripts de la racine sont en `.mjs` sans accès au code de l'API.
Décision :
- Script `apps/api/scripts/seed-fake.ts` (`pnpm --filter api seed:fake`), logique testée dans `src/dev/seed-fake.ts`, comme `grant-admin`. Il crée des comptes `demo.<n>@example.test` vérifiés, avec le carnet personnel et les catégories par défaut de l'inscription, et des dépenses manuelles en EUR (1 € à 150 €, sous-catégories au hasard, 90 derniers jours en heure de Paris). Rejouable : un compte présent n'est pas touché. Mot de passe commun lu dans `SEED_FAKE_PASSWORD` (≥ 12 caractères, jamais dans le dépôt).
- **Garde-fou par le nom de la base** : refus si le nom de la base de `DATABASE_URL` ne finit pas par `_dev`, `_recette` ou `_test`. `DEPLOY.md` impose ces suffixes (la production finit par `_prod`). Pas de garde par `NODE_ENV`, qui vaut `production` en recette.
- Volumes : ≤ 1 000 comptes, ≤ 20 000 dépenses par compte (le banc NF-PERF-02 en utilise 10 000), insertion par lots de 1 000, transaction par compte via `withTransaction` (nouvel essai sur 1213/1205).
- La base de développement Docker est renommée `depenseo` → `depenseo_dev` (script d'init) pour respecter ce nommage ; commande de création manuelle pour un volume existant dans `DEPLOY.md` §1.
- Publication (`DEPLOY.md` §3) : une version par dossier `releases/<sha>` et lien `current`, ordre sauvegarde → migration → bascule ; les migrations doivent rester compatibles avec la version précédente (suppression en deux versions).
Conséquences : renommer une base de production avec l'un de ces suffixes désactiverait le garde-fou. Le nommage des bases fait donc partie de la procédure de déploiement.

## ADR-067 — Limitation de débit de la connexion admin, en 404 (2026-11-05)

Contexte : relecture finale (P7-08). `POST /admin/api/session` ne comptait que les échecs TOTP ; un mauvais mot de passe ne comptait jamais, ce qui permettait de deviner le mot de passe sans limite et de saturer le CPU (hachage à chaque appel) sur l'hébergement mutualisé. NF-SEC-04 impose une limitation de débit sur l'authentification ; NF-SEC-06 impose que les routes admin répondent 404 à qui n'y a pas accès.
Décision : la connexion admin réutilise le garde `@RateLimited` des routes `/auth` (mêmes seaux en base, par IP et par compte, mêmes seuils `AUTH_RATE_LIMIT_*`, fenêtre de 15 min), avec l'option `deny: 404` : au-delà du seuil, 404 sans `Retry-After`, indiscernable d'une route inexistante. Le garde admin (désactivé → 404) passe avant. Toutes les tentatives comptent, réussies ou non, comme sur `/auth/login`.
Conséquences : un administrateur bloqué ne voit qu'un 404 et doit attendre la fin de la fenêtre (15 min) ; c'est documenté ici plutôt que dans l'interface, pour ne rien révéler. Les seaux par compte sont communs à `/auth/login` et à la connexion admin pour une même adresse e-mail, ce qui ne fait que durcir la limite.
